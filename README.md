# puzzly

A Rubik's cube engine built on [cubing.js](https://js.cubing.net/cubing/), with a browser test bench for its scramble, step and full solvers.

## Run

```bash
npm install
npm run dev
```

Then open http://localhost:1234.

## Build

```bash
npm run build
```

The site lands in `dist/web` as plain static files you can host anywhere.

## Rust search

Step searches run in `search/`, a small Rust crate built to WebAssembly, in one worker that keeps what it builds between searches. A goal small enough for one exact distance table (up to 10M states: cross, EO, CO, EOLine, a Roux first block, ZZ blocks after EOLine…) gets one: it's built once (about 50 ms to 0.6 s), then every scramble is answered with a shortest solution right away, without searching. A bigger goal (XCross, XXCross, first layer, DR, F2L pairs, OLL or PLL that keep earlier pieces…) is split into sub-tables that each fit (the goal with some pieces, or their twists, left out) and searched with IDA*, bounded by the largest sub-table distance: still a shortest solution, e.g. XXCross in a few ms instead of up to 9 s, or an OLL step that keeps F2L in about 0.1–0.5 s instead of ~20 s. Sub-tables are planned two ways and both are kept: one fills each table with pieces of its first piece's kind first (all corners together, which sees a PLL's corner cycle or a DR finish's corners), the other with the pieces the same moves turn (a pair's corner and edge share two faces, so F2L pairs are seen whole); either way alone left 2–13× more search nodes on some goal (PLL with keep, XXXCross, F2L pairs). Equal sub-goals share one table (all CFOP pair steps share their "cross + one piece" and "pair + nearby pieces" tables). Sub-tables that are rotated copies of each other are built only once, whatever goal they come from: the cube is turned by a rotation that keeps the allowed moves before the lookup, so one table answers both "cross + DFR" and "cross + DBL", and the table for "4 U edges + DF" also answers for "+ DR" (PLL with keep: 4 tables read 22 ways). The benchmark's methods need 48 tables instead of 84 (69 MB instead of 111), with the same answers and search speed. Each split goal starts on small sub-tables (up to 1M states, built in a fraction of a second) and moves up to bigger, sharper ones one size at a time (10M, then 40M), each time its searches have cost about as much as building the next size would. 40M tables make the heaviest searches (XXXCross, PLL that keeps F2L, BLD flips) about 3× faster, but one method's set can take ~220 MB, so only devices whose browser reports 8 GB of memory or more go past 10M (Chrome and Edge report it, rounded down: a 6 GB PC counts as 4; Firefox and Safari don't, so they stop at 10M). [twips](https://github.com/cubing/twips) is only the fallback for goals that can't be split.

A split goal always gets the biggest sub-tables the device allows: 10M states each, or 40M where the browser reports 8 GB or more (Chrome on a 6 GB PC reports 4). They're built (or loaded from this browser) the first time the goal is searched; a smaller plan is only a fallback when they can't be built. Before, a goal started on 1M sub-tables and moved up after enough search nodes. Since a list stops at a node budget (see *Lookahead*), a later run then reached further and could list other answers, so the same method on the same scramble gave another solve the second time (57 moves, then 21, on one scramble), and the helper threads' node counts moved that switch too. Now a run gives the same solve every time, with one core or four. The cost is the first search of each goal: CFOP level 2's first scramble took 9.1 s instead of 6.8 s in Node (the browser stores the tables, so only once), and every later one the same as before.

Before searching, the worker measures every alternative × grip: the exact distance from a table, or a lower bound from split tables (their largest distance at the start). Combos are searched closest first, and one that can't beat the best answer so far is never searched, so most steps run one or two searches (a pseudo-cross with any bottom face and any front: 4 searches instead of 82). A step's offsets share one table that holds every offset's target, so a pseudo-cross or a pseudo pair is one search per grip instead of one per offset.

For lookahead (see *Method* below) the same tables also list every answer up to a length, not just the first: IDA* keeps going after a hit (shortest answers first, then one move longer…), skipping answers that pass through the goal on the way (a shorter answer plus moves that keep the goal, which the next steps can always make themselves). Listing is fast (Node, 4 scrambles): every shortest cross or pseudo cross in under 1 ms, the 17–500 one move longer in 0.2–11 ms, a pseudo XCross's answers up to two moves longer (250–5,000 of them) in 10–180 ms. A list can also come a page at a time: the answers of one length that come after a given answer (answers come in a fixed move order, so the next page picks up where the last one ended without redoing it). The method search (see *Method search* below) uses that, so it never holds a huge list.

A step with *Solvable with* moves (see *Test bench*) sends them along with its targets: the Rust side closes the targets under those moves (every pattern they reach from them, at most 100,000) and fills the tables from all of them at once, so the answer is still a shortest one. Split goals of this kind also get one table per piece type holding every tracked piece's position (no twists), because such goals limit how the pieces sit as a whole (a 2-gen corner permutation), which tables of a few pieces can't see. A CP line (`DL DFL DBL` plus the other corners `:p`, solvable with R U) is one exact table of 8.7M states (about 1.7 s to build once, then stored), and each scramble's 4–6 move answer takes ~0.1 ms.

A goal with relative groups (`:r`, see *Test bench*) needs nothing new on the Rust side either: the engine sends one target per way its groups can sit (a pair: 24, or 16 with the cross kept, since the pair can't sit on a cross spot), and the tables fill from all of them at once, so answers stay shortest. Cross + a pair joined anywhere is one search of ~10 ms once its tables exist (~0.35 s with the first build).

Blindfolded (BLD) steps keep every other piece exactly as it is, so their goal depends on the scramble. The engine renames the pieces so the wanted end state *is* the solved cube (moves act on spots, not on piece names, so the answer is the same): every BLD step becomes "solve the whole cube" from a cube that's solved except for a 3-cycle, a parity swap or a flip. All BLD steps of every scramble therefore share one set of tables. They also ask for a whole-orbit table (all 8 corners, 88M states, ~7 s to build once, then stored), which sees corner swaps and twists that tables of one corner each can't. 3-cycles take a few ms and parity steps (13–14 moves) 0.01–6 s. Pure 2-edge flips (13–14 moves) are the slow case, 5–40 s, since no table that fits sees them well. The engine remembers every BLD answer while the page is open, and a case doesn't depend on the rest of the cube, so a repeat of the same case is instant.

A table takes a quarter byte per state (10M states = 2.4 MB): it keeps each state's distance mod 3, since one move changes a distance by at most one, so the search works out exact distances from the start's (found by walking down to the goal) move by move. Tables of 100k states and up are stored in the browser (IndexedDB, database `puzzly-tables`), so after a reload they load in a few ms instead of being rebuilt (e.g. CFOP + OLL: about 3 s the first time, under 1 s after a reload). While the worker builds or loads tables, the status line says *building tables…* / *loading stored tables…*, and the final status says how many it built or loaded. After 60 s without searches the worker stops, so its memory goes back to the system; the next search starts a fresh one, which loads the stored tables. Clearing the site's data in the browser removes them (they're rebuilt when needed).

Long searches use more than one core. A split search first runs alone in the worker for up to 20k search nodes (~60 ms), and almost every search ends there. A longer one carries on from where it stopped, one IDA* round (one answer length) at a time. Each big round is cut into tasks by its first two moves (~240 with face turns), handed out one at a time to helper workers and to the worker itself. There is one helper per extra core the browser reports, at most 3, started on the first long search. A round's answer is the one under the first task (in move order) that has one, so every answer is exactly the one a single search gives; tasks after it aren't waited for. Each helper gets its own copy of the tables of the goals it helps with (sent once by the worker, up to 128 MB per helper, 256 MB on 8 GB devices). On a 2-core / 4-thread laptop, heavy searches run 1.4–1.75× faster (XXXCross 0.86 → 0.55 s, PLL that keeps F2L 2.1 → 1.2 s, a BLD flip 3.2 → 1.7 s); the first long search after the worker starts pays ~0.3 s to start the helpers. Lists (lookahead, method search) and table builds still use one core. Where a worker can't start workers of its own, searches stay on one core.

Build it once before `npm run dev` / `npm run build`, and again after changing it (needs Rust, the `wasm32-unknown-unknown` target and wasm-pack):

```bash
npm run build-search
```

## Benchmark

`bench/` times the search on heavy goals in Node (no browser), so a change to the Rust search or the engine can be compared with the code before it. Bundle it after `npm run build-search`:

```bash
npm run bench-build
```

- `node bench/out/record.js [requests file] [scenarios] [passes]` runs five scenarios on fixed seeded scrambles through the real engine and worker: *dr-finish* (DR, then the whole cube with `U D R2 L2 F2 B2`), *xxxcross*, *cfop-oll-pll* (the CFOP example plus OLL and PLL that keep F2L), *pseudo-lookahead* (the pseudo-slotting example) and *bld-flip* (two pure 2-edge flips). It prints each run's moves and time, twice (first with table builds, then warm), and saves every request the engine sent to the worker (default `bench/out/requests.jsonl`). A full run takes 10–20 minutes. Node reports no device memory, so the worker keeps 10M tables; `DEVICE_GB=8` makes it act as on an 8 GB device. The worker sees one core unless `CORES=4` is set: then it starts 3 search helpers in real threads (`bench/out/helper.js`), as on a 4-core device.
- `node bench/out/replay.js [requests file] [results file] [scenarios]` sends those requests straight to the Rust search, each goal on its biggest tables, and prints per scenario: time, search nodes, µs per node, and how far the start bound is below the real answer length. Tables are saved in `bench/out/tables` after the first run (`FRESH=1` builds them again). Split goals use 10M sub-tables, or `BIG=40000000` for the 8 GB size. `CORES=4` spreads long searches over 3 helper threads, the way the worker does (default 1: one core).
- `node bench/compare.mjs before.jsonl after.jsonl` checks that two replays give the same answers (and node counts) and prints the speed-up per scenario.
- `node bench/out/known-algs.js [groups] [extra moves] [names]` checks the speed model against algs solvers agree on (`bench/known-cases.ts`: 19 first-two-layers, 46 last-layer-orientation and 21 permutation algs; groups `f2l,oll` by default, `pll` takes minutes a case). Each alg is undone on a solved cube and given back as a step ranked by speed, with the alg's own extra moves up to the limit (2 by default), once with x turns and once with any front and every axis. It prints, per case, whether the engine's pick is the known alg as written, its turns in another writing or another alg, with both scores, then the totals. The worker's answers are kept in `bench/out/known-algs-cache.json`, so a run after changing only the speed model takes about 3 minutes instead of 8; `PATCH='{"tilt":1}'` tries other numbers of the hand map without editing it. See *Speed* for what it found.
- `node bench/out/alg-sets.js [sets]` checks the alg sets (`src/engine/algs/`, see *Alg sets* under *Speed*; `OLL,PLL,ZBLL` by default) against the cube: it makes all 62,208 last-layer states and asks each set's step to recognise them (216 ways the pieces can be turned for OLL, 288 states for PLL, the 7,776 with the edges oriented for ZBLL). It says which algs leave the cube held another way, which are listed under the wrong case, which cases share a state, and which states no alg fits, and exits with code 1 when a set has any of those. Run it after editing `oll.ts`, `pll.ts` or `zbll.ts`; it takes about half a minute and needs no search worker.
- `node bench/out/zbll-sheet.js <zbll file> [output]` makes `src/engine/algs/zbll.ts` from a published alg database instead of solving each case: the ZBLL file of [@moishy/algsets](https://www.npmjs.com/package/@moishy/algsets) (MIT; its algs come from SpeedCubeDB), read as text and never run. Get it with `npm pack @moishy/algsets@0.3.3` and `tar xzf moishy-algsets-0.3.3.tgz`, then pass `package/esm/src/zbll/index.js`. Each alg is tidied (no brackets, `R2` for `R2'`, `r` for `Rw`, no turn of the top at either end, a rotation it leaves undone at its end), checked on the cube (it keeps the first two layers, leaves the edges oriented and ends held as it started) and filed under the case it really solves, up to turns of the top; the PLL cases are left to `pll.ts`, and it fails if any of the 494 cases (472 ZBLL, 21 PLL, solved) has no alg. Each case's algs are written fastest first by the speed model. It takes a few seconds.

The replay bundle carries the Rust search code it was built with, so to compare a Rust change: record once, copy `bench/out/replay.js` to `bench/out/replay-before.js` and replay with it into `before.jsonl`, then change the code, run `npm run build-search` and `npm run bench-build`, replay into `after.jsonl` and compare.

## Test bench

- **Start position**: a random scramble, or any moves you type (Ctrl+Enter solves).
- **Result**: the solution plays on the 3D cube, with move count, time and a check that it really reaches the goal. *Speed* is the solution's speed cost with its regrips, the hands coming back home at the end included (see *Speed*). Under it, *Fingering* lists every move (and regrip) with the hand and finger that makes it, its score (with its finger regrips, its surcharges for an awkward or twisted grip, a layer turned again, leaving the rhythm or an open opposite layer, and what it saves by keeping the rhythm, all named), the other ways to make it from that hand position with their scores, and where both wrists are after it; it ends with the hands that have to come back home. *Answers compared* lists the other answers the step found (see *Best answer*), each with its moves, speed and check: click one to see it on the cube, and *Continue from here* then goes on from that one. The runs and method tables have a *Speed* column too. The status line notes when tables are being built or loaded, and how many.
- **Done so far**: moves earlier steps did after the scramble; *Continue from here* adds the shown solution here, so steps can be chained (cross, then XCross…). The scramble is judged by its centers; after it only x/y/z change the grip, so M/E/S in a step don't make the next step think the cube was turned.
- **Runs**: every solve this session; click a row to see it again.
- **Goal**: *Step* solves only the chosen pieces (presets, or the chips with *Chip click sets*). `UF` = solved, `UF:p` = in place with any twist, `UF:o` = oriented and may swap with the other `:o` pieces of its type (`:o2`, `:o3`… are separate groups, e.g. DR: U/D edges `:o`, E-slice edges `:o2`), `UF:s` / `:s2`… = anywhere in its group with any twist, `UF:r` / `:r2`… = solved relative to the rest of its group, anywhere (see *Relative groups*), `UF:x` = its spot may change (for *Blindfolded* steps; anywhere else it's the same as leaving the piece out). Pressed chips show their role (`:o`, `:p`, `:r`, `:x`…). Centers `U L F R B D`: none listed = all six kept, otherwise only the listed ones (e.g. Roux first block `L DL FL BL DFL DBL` with M allowed). *Full cube* solves everything.
- **Relative groups**: `:r` (and `:r2`, `:r3`… for separate groups) marks pieces that only need to be solved relative to each other, anywhere on the cube: `DFR:r FR:r` is that pair joined anywhere, `DF DR DB DL DFR:r FR:r` (preset *Cross + front-right pair joined anywhere*) the cross plus that pair joined wherever it doesn't break the cross, `DBL:r DB:r DL:r BL:r` a corner and its three edges as a block anywhere (an FMC pseudo-block). A group may sit wherever turning the whole cube would put it (24 ways), but only on spots of pieces the goal ignores, or of `:o` / `:s` group pieces, which then take the spots it left; pieces without `:r` stay home, and two groups are placed independently. Answers are still shortest (Node, seeded scrambles): a pair joined anywhere 2–3 moves (2–5 into its slot), cross + pair joined 6–7 (XCross 7–9), the block anywhere 5–6 (6–7 at home), each in about 10 ms once the tables exist; cross + two pairs joined (`:r` and `:r2`) 7–8 moves in ~90 ms. With restricted moves, places the moves can never reach are left out (a pair in a slot R U never turn, an edge flipped under U R L). In a method, *Keep earlier steps' pieces* keeps each earlier group joined on its own (groups are renumbered, so a pair joined earlier and one joined now don't have to sit together, and a step joining "the easiest pair" with *any front* skips pairs already joined); to grow a block instead, list its pieces again in the new step's group, e.g. `DBL:r DB:r DL:r BL:r`, then `DBL:r DB:r DL:r BL:r DFL:r DF:r FL:r` (a pseudo 2x2x2, then 2x2x3: 10–13 moves on 4 scrambles vs 11–13 for the same blocks at home).
- **Alternatives**: put several goals in *Pieces*, one per line (*+ Alternative* copies the caret's line below it); any one of them counts. The chips, preset and cube mask follow the line the caret is on, and Enter adds a line (Ctrl+Enter solves). Every alternative × grip (with all its offsets) counts and the shortest wins (combos that can't beat the best aren't searched); on a tie, the alternative that solves more new pieces wins, so `DF DR DB DL` plus a line `DF DR DB DL DFR FR` gives the XCross whenever it costs no extra move. The result's *Alternative* (e.g. 2 of 2), the status line and the runs table say which one won.
- **Bottom face**: which faces may go on the bottom, with beside them the turns an answer may start with: *any front* (y turns). By speed the *Hand turns* rows under it add wide turns, slice turns and rotations (see *Best answer*). Every grip counts and the shortest answer wins; it starts with the rotation to do first (e.g. `x2 L D R D`).
- **Offsets**: the goal also counts when the cube is off by one of these moves, e.g. `D D2 D'` (*ADF*) for a pseudo-cross or `U U2 U'` (*AUF*) for a last-layer step. Spaces separate one-move offsets; use commas when an offset has several moves (`U D, U2`). No offset is always tried too; a grip's offsets are searched together (one table holds every offset's target) and the shortest wins. With *finish with the move that undoes the offset* ticked (the default), a step solve's answer ends with that move, so it counts in the moves and the speed, and the best answer is the shortest or fastest with it: a pseudo-cross one move short of the cross no longer beats a cross of the same length. Unticked, the solution leaves the offset in: the result shows it with the moves that undo it, and a next step needs the same offsets (or those undo moves first). A method step always leaves its offset in, for the steps after it.
- **Solvable with**: the goal also counts when these moves alone can finish it later, e.g. `R U`: `DL DFL DBL UFR:p UBR:p UBL:p UFL:p DFR:p DBR:p` solvable with `R U` is the left line plus corners that R and U alone can solve (the CP step of 2GR or ZZ-d), not the corners in place. Every cube state those moves reach from the goal counts (at most 100,000: give pieces the moves twist anyway `:p`, as above, which leaves 120 states instead of 29,160). The result and the runs table check the answer the same way. Later steps that keep earlier pieces only keep the ones those moves can't disturb (the line here, not the corners), so the steps after it should use those moves only (e.g. *Moves allowed* R U), which keep the property by themselves. If the moves would change pieces (or centers) the step's allowed moves never touch, the step stops with a message instead.
- **Blindfolded**: *keep every other piece untouched* makes every piece the goal doesn't list stay exactly where it is, turned the same way (instead of being ignored).
  - The listed pieces go home, and the pieces they push out fill the spots they leave. `:p` pieces may end with any twist, and `:x` spots may take any piece.
  - Examples: `UR UB UF:x` finds the shortest 3-cycle that solves UR and UB through UF; `UFR:p UBR:p UR UL` finds the shortest T-perm-like swap.
  - A goal no moves can reach with everything else kept (a lone swap or a lone twist) stops with a message.
  - **Buffer**: the step picks its own pieces (leave *Pieces* empty). It follows the buffer's cycle for *targets per step* targets (2 = a 3-cycle): each target sends the piece in the buffer home and brings the piece there into the buffer.
  - When the buffer holds its own piece, a new cycle starts at any unsolved piece; every choice is tried and the shortest wins. With the buffer home, a step may instead fix two pieces that are only flipped or twisted in place, like a flip alg.
  - **Parity pieces** (e.g. `UFR UBR`): when the targets left are odd (a lone swap no moves can do), those pieces swap too, keeping their twists (like a parity alg). Only if that can't work may they end any way.
  - Quick picks: *Edges (UF)* (parity `UFR UBR`), *Corners (UFR)*, *None*. The result shows which pieces went home and which spots changed, and the check also makes sure every other piece is still where it was.
  - Untouched steps take no offsets or solvable-with moves. Their goal is relabeled to "the whole cube" (see *Rust search*), so they share one set of tables.
- **Moves allowed**: face turns plus M, E, S. A letter allows every turn of that layer (R, R2, R'); the second row (`U2` … `S2`) allows only its half turn (ticking both = every turn). Quick picks: *Face turns*, *R U*, and *DR* (`U D R2 L2 F2 B2`, a domino reduction's second phase). E.g. after your own DR step, a step with every piece, *Keep earlier steps' pieces* and *DR* finishes the cube without leaving DR, shortest within those moves (12 scrambles: 12–15 move finishes; the first few solves take 1–2 s while the tables are built, then finishes take 6–260 ms). In method files these are plain moves like `"R2"`. If a step keeps centers that are out of place and its moves can't bring them home, it stops with a message instead of searching forever.
- **Best answer**: what wins among a step's answers. *Avoid faces* (e.g. `F B`) comes first. By moves, an answer that turns none of those faces comes before all others, whatever its length, so give such answers room with extra moves. By speed, an answer that turns some of them only loses outright to one held the same way that doesn't. Everything else is ranked by speed together, since a rotation's cost (3, or 4.5 for a y2) is in the score: an answer on other faces after a rotation, one that needs no rotation, and one that has to turn the faces because nothing held that way does without. So `F' U' F` (5.3) beats `y' R' U' R` (5.4) in the middle of a solve, a quick `y' U' R U' R' U R U' R'` (8.9) beats a slow `D L' U L U' L' U L D'` (10.05) that needs no rotation, and on a solve's first step, where the rotation is free, the answer on R and U wins. An answer that turns L while R is a quarter turn open (`R U L' U2 L R'`, see *Regrips and grips*) counts like one that turns an avoided face. It's for first-two-layers pairs, where an answer on R, U and L turns faster and takes almost no regrips. Then: *Speed* (the default) takes the answer with the lowest speed cost (see *Speed*); on a solve's first step (nothing in *Done so far*) a grip rotation costs nothing, so with *any front* ticked it picks the front too. *Fewest moves* takes the shortest. *Hand turns* (by speed: three rows under *Bottom face*, each with x, y and z boxes, x and z ticked by default) say how the hands may make an answer's turns, each kind on its own. *Wide* writes it with wide turns that cancel out (`r U R' U' r' F R F'` with Rw Lw, `f R U R' U' f'` with Fw Bw); *Slice* with slice turns, alone or with wide turns (`M2 U M U2 M' U M2` with M); *Rotations* lets the cube turn in the middle of an answer: with x, after a solve's first step, the cube tilted for it and tilted back (`x R2 D2 R U R' D2 R U' R x'`). With a wide turn and a rotation on the same axis, one R or L turn may also be made as the other hand's wide turn (R' as Lw' after an x), and the same with F and B (Fw, Bw) or U and D (Uw, Dw): an x, z or y turn first, or last, makes up for it, so the cube ends exactly as the plain answer leaves it. *Add form as step* saves them with the step (`wideAxes`, `sliceAxes` and `rotationAxes` in a method file; a file with only `wideAxes`, from before they were apart, means it for all three), and the method's rows then show the wide writing, like a step solve. So *Solve* and *Run method* give the same cross when the form and the step say the same. *Up to N extra moves* (2 by default) also compares answers that many moves longer than the shortest: by speed one of them may win, and a method step's lookahead judges them too. They're listed one move longer at a time within a search budget of a few seconds, so a step far from its goal may compare fewer. *List N other answers* shows that many more under the result, best first (shortest first, or fastest first by speed); 0 lists none, which is the fastest search (a long last-layer step takes several times longer when it has to list its answers).
- **Method**: a list of steps run in order, each from where the last one left the cube (after *Done so far*). The form on the left is the step editor: set it up, give the step a name, then *Add form as step*; *Edit* loads a step back into the form and *Update step N* saves it. *Keep earlier steps' pieces* adds every earlier step's pieces to the goal (this step's roles win; centers only change when the step lists some). Only the grips where the fewest of the step's pieces are already kept get searched, so a grip turn can't swap the step's pieces for ones already done: `DFR FR` with any front means "the easiest pair not done yet", and an OLL step can't turn the solved first layer to the top. A step whose pieces are all done already in the grip it's held in (e.g. the last pair after an XCross) answers with 0 moves. A later step that places one of a step's alternatives along with pieces of its own (*Last pair + EO*: a pair slot plus the EO edges) gets one left for it: once no more slots are free than such later steps, the step is held back and answers with 0 moves, held as it is (in the ZBLL example, *Pair 3* after an XCross), so the last pair still goes in with its EO instead of EO being made on a finished F2L. *Repeat until done* runs a step again and again, until a round has nothing left to do (0 moves); each round gets its own row (*Edges 1*, *Edges 2*…). That's one 3-cycle per round for BLD, or "the easiest pair" with *any front* until F2L is done. *Alg set* (OLL, PLL or ZBLL) answers the step from a set of known algs instead of a search: the case is recognised and its usual alg made (see *Alg sets* under *Speed*); the step's row then names the case, like *PLL (T perm)*. *Run method* lists each step's solution and moves; click a row to see it on the cube. The *Total* row joins a step's first turns with the moves before it: R then R' is nothing, U then U is U2, a turn after the step's grip rotation counts as the face it really turns (U then y U' is y, R then y F' is y), a turn on the same axis in between doesn't stop it (R L then R' is L), and whatever a cancelled pair brings together is joined too. Where a step that keeps earlier pieces cancels into the answer before it, the rows show it the way an XCross shows its pair: the answer before it takes both, joined, and the step is done with 0 moves (*Pair 4* `U' R U R'` then *OLL* `R U R' U R U2 R'` is *Pair 4* `U' R U2 R' U R U2 R'`, *OLL* 0 moves), so the rows add up to the *Total*. An alg step left with only its AUF (a PLL skip) goes with the answer before it too when the steps between them were done with 0 moves, by such a join or by that answer itself (*Pair 4* `U' R U2 R' U R U2 R' U`, *OLL* and *PLL* 0 moves). Search fastest and Search fewest moves start from the rows as each step answered and only show them joined. Steps ranked by speed count those cancels when they pick their answer (see *Ranking by speed*). *Save* keeps the method in this browser; *Export file* / *Import file* share it as JSON.

- **Lookahead style** (per method step, by speed): *human* (the default) also pays for the solver's eyes: finding each step's pieces, leaving the next step's in sight (so a pair step may rotate where F turns would leave the next pairs at the back) and turning the cube in the middle of an answer (see *Finding pieces* under *Speed*). *Efficiency* ranks by how fast the moves turn and nothing else, so the F turns win wherever they turn faster. On 8 seeded solves of the CFOP example with the same cross, switching its pair steps to efficiency changed the pairs of 3 solves (7 rotations → 6, 16 F and B turns either way) and halved the time (3.7 → 1.7 s per solve, the looks left unscored).
- **Lookahead** (per method step, under the step name): on its own, each step takes its shortest answer, so a method never accepts a slightly worse step that sets up the next ones. With *Lookahead N steps*, the step lists its candidate answers (every alternative × grip × offset: all its shortest answers, plus answers up to *extra moves* longer, at most 64, shortest first), runs the next N steps after each one (each taking its own shortest answer), and keeps the candidate with the fewest moves in total; on a tie, its own shortest answer stays. N has no upper limit: past the last step it stops at the end of the solve, so a number at least as big as the steps after it judges each candidate by the whole rest of the solve (a repeated step counts its rounds). A step that's only judging (it's solved once per candidate) compares one extra move at most, whatever it was given, so judging stays quick; when the run gets to that step it compares all of them. With three extra moves on its pairs, the cross-or-XCross example's first step took 18 s judged in full and takes 2.3 s this way. *Over its best N answers* (`candidates` in a method file) says how many of the step's answers are followed, best first (64 at most). They're followed one after the other, and one whose own cost is already no lower than the best total so far isn't followed at all. Fewer is quicker and lost nothing measurable. With the ZBLL example's steps on 6 seeded scrambles, its ZBLL searched on R, U and L for this comparison so that the last step's search didn't drown the rest (speed cost summed over the solve, seconds a solve in Node): no lookahead 61.2 in 3.5 s; the first step judged by the next one over 64 answers 57.7 in 4.9 s, by the next two 56.0 in 5.9 s; by the next two over 16 answers 55.0 in 3.7 s, and by the next three 54.1 in 3.7 s. Each step trusts an estimate of the next one that the next one, looking ahead itself, then doesn't keep to: with lookahead on every step a pair was taken at 9.1 instead of 7.6 for a three-move next pair that was never made, and a solve took 30 to 50 s. So the examples plan the first step only, which is what inspection is for. That's what makes pseudo-slotting and free XCrosses pay off: a pseudo pair that leaves the cube off by a D turn, or an XCross two moves longer than the cross, wins when it saves more in the next step. Lookahead 0 (the default, and what old method files get) gives exactly the answers it gave before. *Extra moves* is the step form's field under *Best answer*. A step ranked by speed judges its candidates by speed cost instead of moves: its own plus the next steps', each of those taking its own best answer.
- **Method search** (*Search fewest moves*, under *Run method*, with a time limit in seconds): looks for the run of the whole method with the fewest moves in total, where any step may take a longer answer if that saves more moves later. It counts moves only, whatever the steps' *Best answer* says.
  - It starts from *Run method*'s answer (with the steps' own lookahead) and only looks for runs with fewer moves. Each shorter run replaces the rows as soon as it's found (the *Time* of the total is when it was found), and the best one goes to the cube and the runs table at the end.
  - It goes through each step's answers shortest first. Before going on from an answer, it measures how far the next step is, and how far a later step's goal is from there. For example, after a CFOP cross every run still has to reach F2L. Those goals are worked out from the method alone: the steps' alternatives and grips, which earlier pieces they keep, and every move the steps in between may use. An answer whose rest can't get under the best total is skipped, and so is a cube state reached before with no fewer moves. The last step just takes its shortest answer within the moves left.
  - It stops at the time limit or when you press *Stop search*, keeping the best run. The status shows the fewest moves any run can have (*at least N moves*). When the search gets through everything, or finds a run that short, the status says the run is *the fewest this method can do*; otherwise there may still be a shorter one.
  - Rules: a step's answer never passes through its own goal on the way (as with lookahead), *Max depth* still limits a step, *stop at first answer* is ignored, a repeated step is searched round by round, and the offset the last step leaves isn't counted (a fix step like *ADF* counts like any step).
  - Examples (Node, 30 s after one plain run built the tables; plain run → best found): DR then a `U D R2 L2 F2 B2` finish on 4 scrambles 19 → 19, 23 → 17 (in 0.7 s), 22 → 20, 25 → 20 (in 0.6 s), where cubing.js's two-phase full solver gives 19, 20, 20, 21. CFOP 31 → 20 and 31 → 23, ZZ 23 → 16 and 28 → 17, ZZ with CP and R U 36 → 26 and 42 → 27, pseudo-slotting 23 → 22. Small two-step methods (cross then a pair) finish in under a second and are proven the fewest, often straight from the bound; whole CFOP or DR runs can't be proven in that time (their bound is 7–8 moves, far below the 16–27 a run takes).
  - It measures roughly 1,500 step starts per second. The slow part is listing many long answers of a big step (every 12-move DR takes seconds), so it improves fastest on methods whose steps have few answers of each length.
- **Search fastest** (beam search, under *Search fewest moves*, keeping *N* per pieces done): looks for the solve of the whole method with the lowest speed cost, counted as a lookahead counts it: each step's turning after the moves before it (cancels count) plus what finding its pieces costs (each step's *Lookahead style*). It's the computer-efficiency mode: a lookahead judges each answer by the next steps' own best answers only, so it can't see a chain like an XXCross whose pairs end in a cancel into OLL and a PLL skip; the beam can, as long as that chain stays among the cheapest at every step.
  - It first runs the method as *Run method* does and keeps that run's path at every step, so it never ends above it. Then, step by step, every partial solve goes on with each alternative's best *N* answers by speed, and the cheapest *N* partial solves of each set of pieces done are kept (more when few sets are left, as many in all as 8 sets would have: the last layer keeps 8 × *N*). A cross is never ranked against an XXCross, nor a pair in front against one at the back: they meet once both have the same pieces done. The same cube reached twice keeps its cheaper way.
  - Every step ranks by speed here, and the steps' *Lookahead* and *over its best N answers* aren't used (the beam is the lookahead). The first step compares all its extra moves; later steps one at most, as a lookahead's judged steps do (the seed's own steps compared all of theirs).
  - Answers per alternative: the step lists each alternative's best *N* apart (`perAlternative` in `stepCandidates`), instead of sharing the places by size. Placements that are rotations of each other (an XCross at FR or at FL) are searched once and their answers scored in each twin grip, so they count as alternatives of their own. Shared by size, the twelve or so places of a two-pair first step went to 10–12-move answers that leave the next pair in sight, never to an 8-move XXCross on the side the pairs were wanted.
  - *Stop search* finishes quickly: from then on one partial solve per set of pieces done goes on, each step with its own best answer. The status gives the cost, how much of it is finding pieces, and the plain run's cost.
  - Measured (Node, CFOP level 2, 6 seeded scrambles, seed 55; cost = turning plus looks): plain run 74.6 (61.2 turning, 52.2 moves, 7 s a solve); *N* = 4: 59.8 (47.2, 39.5 moves, 19 s); *N* = 8: 60.3 (47.5, 39.8 moves, 32 s), the plain run included. *N* = 4 beat the plain run on all 6. A wider beam isn't always better: on one scramble *N* = 8 kept the plain run (69.8) where *N* = 4 found 64.2, since each set's share of places changes with *N*. Each kept partial solve costs one step's listing, so the time grows about as fast as *N*.
  - On a scramble with a 21-move speedsolver solve (an 8-move XXCross on the left, two right-hand pairs, a Sune cancelling into the last pair, a PLL skip), a CFOP method with every pair placement on its first step (white bottom, face turns, 4 extra moves) went 73.6 → 58.8 at *N* = 4 (38 moves) and 73.6 → 49.8 at *N* = 8: a 21-move solve, `x2 x' D' R D' U2 Rw D R2` / `R2 D' F D R2` / `y U R' U R` / `U' R U R'` / Sune / `U`, ending like the speedsolver's and cheaper by this count than their line as the engine writes it (51.3, more looks); about 2 min a solve, most of it the first step's listing.

## Speed

A move count doesn't say how a solution turns in the hands. `src/engine/speed/` scores that: `fingering(moves)` finds the cheapest way two hands can make a move sequence and says who makes each move, and `speedCost(moves)` is its cost alone, where an easy turn (R, or a U flick) is 1. It only reads move text, so it needs no search worker. A step can rank its answers by it (*Best answer* in the test bench, `rank: "speed"` in the engine and in method files); left alone, steps still take the fewest moves, with exactly the answers they gave before.

- **Wrist positions**: each hand is in one of three, named by where its thumb sits: *home* (on the front), *down* (on the bottom: the right hand after R') and *up* (on top: after R). R, R' and R2 are wrist turns of the right hand, L, L' and L2 of the left. A wrist can't turn past *down* or *up*, and a half turn goes from one to the other, so R2 from home takes a regrip first.
- **Hand map** (`HANDS` in `hands.ts`): for each wrist position, the turns each finger can make and what they cost. It lists the right hand; the left hand's tricks are the mirror image (U ↔ U', F' ↔ F…, M turns stay as they are). A turn may have several tricks at one position; the cheapest is used and the rest are its other ways.
  - **The fingers keep their tricks as the wrist turns**, on whichever layers they then lie on. The index finger's U tricks are F tricks with the thumb on the bottom and B tricks with it on top; the ring finger's D tricks are B tricks with the thumb on the bottom and F tricks with it on top (so after L the left ring finger turns B, and after R the right ring finger turns F'); the middle finger's E' is S, then S'. Pushes don't follow: a finger can only push a layer it reaches from behind (U and D at home, and U for the index finger with the thumb on top), so no index push turns F' or B'.
  - **Costs go by kind of trick**, one number each at the top of `hands.ts`: a flick 1 (the finger pulls its layer), a double flick 1.6 (with the finger beside it, a half turn: slower than a flick, but not by much: `R U R'` 2.4, `R U2 R'` 3), a push 1.2, a thumb push 1.5 (a short drag by the finger the hand holds the cube with). The table shows these; what the layer itself adds is under *Layers* below.
  - **Reaches** (marked * below) are tricks a finger has to leave its place for, so each also costs a finger regrip (0.6, counted in the costs shown): F at home with the index finger or the thumb, every slice turn, every push, D' from the thumb-on-top position, and every wide turn (see *Wrist turns and the rest*). So only wrist turns and plain or double flicks turn without one.

  With the left hand's mirror images most turns have several ways. U after R: the right index finger (1), or a left index push (1.8). F', with its layer's 0.2: the left index finger with the left thumb on the bottom (1.2), the right ring finger with the right thumb on top (1.2), or at home the left index finger (1.8) or the right thumb (2.3), both reaches.
- **Wrist turns and the rest**: a wrist turn costs 1 (a half turn 1.4). A wide turn takes a finger regrip (0.6, as a reach does), whoever makes it: the hand opens to take a second layer along (Rw 1.6, Lw 1.85 with L's 0.25), or the finger moves over to turn two layers (Uw 1.6 with the index finger at home, Fw…); `wide` adds more on top (0 by default). A thumb can't take a second layer along, so it makes none. A move no trick makes (E2, S2, notation the model can't read) costs 2.5.
- **Layers**: how well a layer turns is added to every turn of it, whoever makes it, in the order solvers rank them: nothing for R and U, 0.25 for L (the weaker hand's wrist: known algs turn R where their mirror image would turn L), 0.3 for F, 0.4 for D (a ring finger's turn) and 0.6 for B. Turning B again in the same step costs 1 more each time (`again`, counted from the step's start or the last rotation): one B is a quick flick, B after B isn't. So of two ways to hold the same turns, `y2 B U B L' F D` (11.15) loses to `y L U L F' R D` (9.55), though the second takes two more regrips.
- **Rhythm** (turns per second): a turn of R, U or L made right after another turn of those layers, with no hand regrip in between, keeps the hands' rhythm and costs less (`flow`: 0.3 off for R and U, 0.15 off for L). So a run on R and U is the fastest thing to turn: `R U R' U'` costs 3.1, and the eight turns of `U R' U2 R U' R' U' R` (6.5) beat the six of `D' U2 R U' R' D` (7.1) and the five of `D L U' L' D'` (7.25). A turn of D or B leaves that rhythm, since the hand reaches under or behind the cube: 0.3 more (`leave`), once per run of such turns. F doesn't, since the fingers that turn U turn it (`R' F R F'` costs 5.2). So a first-two-layers pair comes out on R, U and L without D being taken out of the step's moves, while a step that needs D (a keyhole, a pseudo-slot's offset) still turns it: there every answer pays.
- **Regrips and grips**: a regrip (one hand lets go and takes the cube again at another wrist position) costs 1.8 between turns, and 1 when the hand comes back home. Before the first turn of a solve one hand regrips for 0.5 (it's done during inspection), but a second hand pays the full 1.8 there: starting with both hands regripped is awkward. Before a later step's first turn a regrip costs like any other, since the hands come straight from the step before: no step can start with a nearly free regrip to get round an awkward grip. After the last turn each hand that isn't at home costs 1 (it has to come back), so a fingering that ends at home, or nearer to it, wins. Every move made from, or ending in, a grip with both hands away from home costs 0.7 more (an awkward grip: both thumbs on top, or both on the bottom), so the move that takes the second hand away pays too. After R U the right thumb is still on top, so in `U2 R U L' R' U L` (8.1) the L' is awkward, and `U2 R U R' L' U L` (6.6), which brings the right hand home first, wins. Turning L while R is a quarter turn off costs 0.8 more on top (`open`; 0.3 for R against an open L, the stronger wrist), whatever was turned in between and however the hands grip: the hand on the open layer can't hold the rest still, and a U in between doesn't change that. It's counted within a step, from its start or the last rotation (the hands take the cube again, and R and L may be other layers then): in a whole solve, a cross that turns R an odd number of times doesn't make every later L pay. So `R U L' U2 L R'` costs 8.2, and `R' L' D2 L U L' D2 L U' R U` 18.45, more than the A perm it stands in for. Wide and slice turns are left out of this: known algs make them freely against an open layer (`r U R' U' r' F R F'`). The search lists turns of opposite faces in one order only, so a step ranked by speed scores each answer in every order of such turns, in each grip, and keeps the fastest. Bringing a hand home, or tilting the cube back (below), beats turning on in such a grip. With the wrists turned opposite ways the grip is twisted (one thumb on top, the other on the bottom: what R then L, or R' then L', would leave), and that costs 1.2 instead, on the move that ends in it as well as on every move made from it; so the model grips another way first: `R' L'` costs 5.05 with a regrip and never twists. An open opposite layer and an awkward or twisted grip on the same move are the same strain (the hands can't hold the rest still), so only the bigger of the two is paid: the L2 of the cross `y2 R' F' L2 D' R2` paid 0.8 + 1.2 and now pays 1.2 (the cross 13.75 → 12.95).
- **Finger regrips** (0.6, less than any hand regrip between turns): one finger goes somewhere else while the hand keeps its grip. A reach costs one (above). So does a move that needs a finger the move before left out of place, when the same hand made that move and hasn't regripped since: a finger that has to make this move too, or the last finger holding the cube from behind. After D' with the right ring finger, a right-hand U2 (index and middle) has nobody at the back, so the ring finger comes back first: `L D' U2 L'` costs 6.25, the U2 1.6 + 0.6. With the other hand free it makes one of the two moves and nothing is paid (`D U2` at home: left ring finger, then right hand), and a finger is back in its place by itself once another move has been made (in `R U R' U R U2 R'` the index finger is never late).
- **Rotations and tilts**: a rotation costs 3, and a half one (y2, x2, z2) 4.5, since the cube turns twice as far; both hands end at home. So a pair made with `y2 R U2 R2 U' R` (9.3) loses to the same turns on the left hand, `L U2 L2 U' L` (5.85), even when the y2 sets up the next pair on R and U. Before the first turn of a solve (nothing was done before the step) it's free, since the cube is picked up that way: with several grips allowed (*any front*), a first step ranked by speed also picks the front that turns best. An x turn can also be a tilt, made by both wrists together without letting go: x takes both wrists a step up, x' a step down. A tilt costs 0.5 per quarter turn wherever it leads, back home too: both wrists turn with the whole cube in them. So ending on a tilt is no way round a regrip: `R U R' U' Lw' U R U' x'` (8.55) doesn't beat `R U R' U' R' F R F'` (8). A whole answer can be tilted though, as algs with F and B turns are learnt: `R2 B2 R F R' B2 R F' R` (18 as written) is the A perm `x R2 D2 R U R' D2 R U' R x'` (13.8), see *Ranking by speed*.
- **Evaluation**: before every move each hand may regrip to any position, and the cheapest whole sequence wins (9 wrist states, each with the fingers the last move left out of place; about 13 µs per move for the cost alone). So a regrip is only paid where no finger reaches the turn, and it's placed where it helps the moves after it too. Each move of the result has the hand and finger that makes it, its own cost (its layer's included), its finger regrips, its surcharges for an awkward or a twisted grip, for a layer turned again, for leaving the rhythm and for an open opposite layer, what it saves by keeping the rhythm, the regrips before it with theirs, the other ways to make it from the same hand position with their costs, and both wrists after it; the result ends with the hands that come back home. A whole method run is scored as one sequence with each step's start given (`MethodResult.starts`, passed to `speedCost` and `fingering`; the total row does this): the hands carry on from step to step, but the counts that belong to one step (a layer turned again, an open opposite layer) start over. A step's cancel saving is worked out the same way (`StepOptions.previousStarts`).
- **Ranking by speed** (`rank: "speed"` in a step's options and in a method step): the step lists its answers, the shortest ones and those up to `extraMoves` longer (up to 1,000 per alternative × grip), gives each its speed cost (grip rotation included, so a `y` first costs 3) and takes the lowest; `stepCandidates` gives them fastest first. The answers longer than the shortest are listed one move longer at a time, and the listing stops once the step has spent its search budget (`LIST_NODES`: a million search nodes, a few seconds), so a step far from its goal, like a 13-move last-layer case, compares fewer extra moves than it was given, or only its shortest answer, instead of searching for minutes. Not every listed answer is scored: `speedFloor` gives a lower bound of an answer's cost from its text alone (each turn at its cheapest trick, with what it pays or saves whoever makes it, and no regrip at all), about a hundred times quicker than the cost itself, and an answer whose floor is above the slowest of the answers already sure of a place can't make the list. With extra moves most answers are long ones that a good short one rules out this way: with three extra moves a pair step scored for 3.3 s and now for about a second, with the same answers. The scoring also gives the page a turn every 25 ms, so a timer keeps running and the page still answers while a step ranks thousands of answers (it runs on the page's thread; only the search is in the worker). Each answer is scored in the fastest order of its moves: turns about one axis in a row (`L' R'`) can be made in either order, the search lists one, and the hands may turn the other faster (see *Regrips and grips*). Each answer is also tried in the other grips that ask for the same thing (a cross with *any front*: the very same turns held with each front, so renamed), as answers of their own: `L' B L' U' F' L2` and `y' F' L F' U' R' F2` are both listed, each with its score. With `undoOffset` (a step with offsets) every answer goes on to undo the offset it reached, and is measured with those moves, by moves as well as by speed: on seeded scrambles the shortest pseudo-cross with its D turn was exactly as long as the shortest cross. With `wideAxes` ("x": R and L, "y": U and D, "z": F and B) and `rotationAxes` on the same axis, each answer is also tried with one such turn made as the opposite wide turn: R is Lw then x, so the left hand turns two layers while the right holds its own still, and nothing is regripped. The cube's turn is made up by a rotation first (free at the start of a solve, the moves before the wide turn then named for the cube held that way) or by a rotation last (which costs one). Either way the cube ends exactly as the plain answer leaves it, so it works for any goal. Each answer also gets its cheapest writing with any number of wide turns about the `wideAxes` and slice turns about the `sliceAxes` ("x": M, "y": E, "z": S; left out = the wide axes) whose cube turns cancel out, so that no rotation is needed (`cheapestWriting`: one search over every such writing at once, about 5 times a plain score with x alone): `L F R' F' L' F R F'` (13.1) becomes `Rw U R' U' Rw' F R F'` (8.7; `Rw U R' U' L' U Lw F'` is 9.4), `B U L U' L' B'` (13.3) becomes `Fw R U R' U' Fw'` (7.9, with z), and the eleven face turns of a U perm become `M2 U M U2 M' U M2` (11.2). It takes the plain writing's place when it's faster. With "x" in `rotationAxes` (left out = the wide axes), after a solve's first step (which picks how the cube is held for free), each answer with two or more F or B turns is also tried with the cube tilted: an x or x' first, the moves named for the cube held that way, and the tilt back, with a turn of the top layer at either end left outside the tilt (`U2 x … x' U'`); the fastest of these takes the answer's place too when it beats the others. Such a result has two writings: `wide`, as the hands make it, is what's scored and shown; `solution` says the same with the turn itself and a rotation (`R' x` for `Lw'`), since the engine tells how the cube is held from x, y, z turns alone, and is the one to check and go on from. On the scramble `D2 L' F' B' R' D L D' F' D2 L D2 B2 R U2 F2 R U2 R U2 F2` the fastest cross without wide turns is `L' R' F R2 B` (8.65); with x turns and any front it's `y2 x' L' U L2 Lw' F` (6.8): five turns, no rotation after the start, no regrip, the left hand home again after Lw'. With no extra moves the answer is still one of the shortest. With `avoid` (faces) each answer gets a `tier`, and a lower tier always comes first. By moves: 0 turns none of the faces; 1 turns some where no answer held the same way does without; 2 turns some although an answer held the same way doesn't. By speed only that last kind comes later (tier 1; an answer that turns L against an open R counts as turning a face): rotating to avoid the faces, staying, and turning them where nothing held that way does without are all tier 0, so the speed score decides between them. A method step with lookahead and rank speed compares speed costs over itself and the next steps. When a step gives several answers (lookahead) and its alternatives add different numbers of new pieces (`cross | XCross`), each size is listed and ranked apart. It's listed up to its own shortest plus `extraMoves` (at most twice the extra moves past the step's shortest) and ranked with its own bar. The places are shared out equally, and the best of the rest fill any left. Before this, an XCross never made a cross's 16 judged answers: by its own cost it ranked #120 to #335, or below #400, on 12 seeded scrambles. Scored before the rhythm costs, on seeded scrambles (Node): a cross with any front, 7 moves at 13.9 → 7 at 8.8 held with another front, and 6 at 13.2 → 6 at 9.0; CFOP's cross and 4 pairs with 1 extra move, 28 moves at 55.6 → 30 at 48.2, and only 29 at 52.8 → 30 at 52.2 (each step takes its own fastest answer, which can leave the next one a slower start; lookahead is what judges that); a cross with lookahead and the 4 pairs, 26 at 53.5 → 24 at 42.3 and 29 at 59.7 → 25 at 39.9; pseudo-slotting with lookahead, 23 at 46.6 → 25 at 41.8. Ranking a cross took 50–650 ms then and a lookahead method 1.4–6 s per run; a cross with x and z turns, where up to a thousand answers per grip are scored and written out, now takes 0.8 s with one extra move and 2.5 s with two (the writing itself is bounded by the same bar, and its plan only looks at the ways of holding the cube an answer can pass through). In a method each step also gets the earlier steps' moves as the hands make them (`previous`, joined as the *Total* row joins them): an answer whose first turns cancel into them (`… R` then `R' U …`, an AUF into the last pair's U) is scored by what's left of it, less what the earlier moves no longer turn (`speedCostAfter`), and a lookahead counts its totals the same way. Only answers whose first turn can meet one of those moves' last turns are joined at all, so the scoring costs about the same (16 pair steps: 10.0 s → 10.35 s). On 8 seeded solves of the ZBLL example the speed went 61.85 → 59.57 and the moves 44.1 → 42.9; plain CFOP without lookahead stayed about the same (67.2 → 66.9), with cancels between steps up from 10 to 17 in 20 solves. The method search (*Search fewest moves*) still counts moves only.
- **Examples**: `R U R' U'` 3.1 (three of its turns in rhythm) · `R' F R F'` 5.2 (F with the right index finger 1.3, F' with the left index finger 1.9, a reach) · a T perm (14 moves) 12.6 with no hand regrip · `F2` alone 4.7 (right thumb to the bottom first, and back after) · `L B L'` 4.4 (B with the left ring finger, 1.9 with its layer and for leaving the rhythm) · `R B R' U R B R'` 9.2 (the second B costs 1 more) · the U perm `R2 U R U R' U' R' U' R' U R'` (11 moves) 14.6 with 4 regrips (the last one back home) · the cross `L' B L' U' F' L2` 12.65, or 10.35 held with another front (`y' F' L F' U' R' F2`, the rotation free at the start) · `x' L' U L2 Lw' F` 6.8 (started with x', the R' made as the left hand's wide turn: no regrip, both hands home at the end) · the A perm `x R2 D2 R U R' D2 R U' R x'` 13.8 (a tilt each way, the left hand home again after the first).
- **Alg sets** (`algs: "OLL"`, `"PLL"` or `"ZBLL"` in a step's options and in a method step): a last-layer step isn't searched but recognised, as solvers do it. The set holds every case with its usual alg first and a few other common ones after it (`src/engine/algs/oll.ts`: 57 cases, 89 algs; `pll.ts`: 21 cases, 33 algs; plain lists to correct and add to). ZBLL solves the whole last layer in one alg once its edges are oriented: `zbll.ts` holds its 472 cases with 1 to 5 algs each (1,896 in all), named by the corners' pattern and a number (*ZBLL T 1* … *ZBLL AS 72*: T, U, L, H, Pi, S and AS, after the OLL the corners make). They come from a published alg database, not from the engine's own search (see `zbll-sheet.js` under *Benchmark*), and each case's algs are listed fastest first by the speed model. The ZBLL set adds the 21 PLL cases (corners already oriented), so one ZBLL step finishes any last layer whose edges are oriented: 493 cases, 1,929 algs. `algCandidates` tries each alg after each turn of the top layer, and with one more turn after it when the goal needs it; the algs that reach the step's goal are ranked like any answers (by speed, or by moves), the case's first alg winning a tie, and the best one is the step's answer, with the case's name in `alg`. When the goal solves every edge and corner (a PLL or ZBLL step that keeps the first two layers) it doesn't try them all: a lookup made once per set and goal (each alg, with each turn of the top after it, undone from the goal's cube) says which algs can solve the cube, and only those are checked. The answers are the same as trying every alg (checked on 400 PLL and ZBLL steps), but a ZBLL step takes about 3 ms instead of 0.6 s (0.4 s the first time, which makes the lookup). Algs are written as solvers write them (`r`, `M`, `x … x'`) and each ends with the cube held as it started; `wide` gives the alg as written (the one scored and shown), `solution` the face turns it makes on the cube (`toFaces`). No search worker is needed, and a step takes a few hundredths of a second where the search took 3 to 30 s. Only a cube that fits no alg of the set is searched, with the step's other settings, so a set with a case missing still works. On the two solves this was tuned on, the searched last layer gave `R' L' D2 L U L' D2 L U' R U` and `Lw F U' B2 D L' D' B2 U2 F' R' F U' x` (speed 25.35); the sets give `U2 x R2 D2 R U R' D2 R U' R x' U'` (Ab perm, 16.4) and a T perm with a turn of the top after it (13.6). `node bench/out/alg-sets.js` checks the sets against every last-layer state (see *Benchmark*): every alg solves the case it's listed under, and no state is left without one.
- **Checked against known algs** (`bench/known-algs.ts`, see *Benchmark*): this checks the search and the scores, not the alg sets. With x turns and up to 2 extra moves, a searched step's pick is the known alg exactly as written for 12 of 19 first-two-layers cases and 29 of 46 last-layer-orientation cases (12 and 31 with any front and every axis). Before the rhythm costs it was 13 and 32 (13 and 35): turns on R, U and L got cheaper against F, so some picks moved to another writing of the same turns or to another alg. In 8 more last-layer cases the pick is the known alg's turns in another writing (5 with every axis): `R U R' U' Rw R' U R U' Rw'` for the `M'` of OLL 57, `Rw U Rw'` where a left-handed alg ends on `L F L'`, and two `f` algs that x turns alone can't write. In the other 7 and 9 (10 with every axis) it picks another alg: five known algs are 3 or 4 turns longer than the shortest answer, so 2 extra moves never list them (`R U R' U' R U R' U' R U R'`, 11 turns, scores 8 for its rhythm, below anything listed there); a few need a turn x turns can't write (`d'`, `f`, the `M2` of OLL 20); one is an exact tie; the others score 0.3 to 3.6 lower than the known alg, like `R U' R' F' U2 F` (7.8) against `U' R' F R F' R U' R'` (8.3), or `F U R U2 R' U' R U R' F'` (10.8) against OLL 13's `F U R U' R2 F' R U R U' R'` (11.6). Permutation algs are mostly 2 to 4 face turns longer than the shortest answer, so a search only finds them when its budget reaches that far: one more reason the CFOP examples take them from an alg set.
- **Finding pieces** (`LOOK` in `look.ts`, the model's eyes): before each step a solver pauses to find its pieces, and pauses less when the pieces were in sight during the step before (lookahead). In a method, steps ranked by speed pay for that pause.
  - **Cost**: 2 when the pieces and the spots they go to are in plain sight, plus up to 3 more the more of that is out of sight (`step` and `hidden`).
  - **Sight**: a piece counts as seen when two of its stickers are on faces the solver sees: U and F face them, R and L at a slant, B and D not at all (`faces`). So a pair in a back slot, or under the back of the top layer, is half hidden and costs 3.5; a pair in the front costs 2. Only where a piece sits counts for pieces that go anywhere in a group (`:o`, `:s`, `:r`).
  - **Free looks**: a solve's first step pays nothing, since it's planned in inspection. So does a step with nothing left to do (the pair an XCross already did) and a BLD step, since nobody looks at the cube there.
  - **Step ranking**: each answer pays for its own pieces, so of two pairs the one in sight wins. When the method has a step after it, the answer also pays for the next step's pieces, on the cube as the answer leaves it. That's the easiest piece set the next step could take (the solver picks the one in sight), with every set it could take counting half (`later`). So a rotation that brings the next pairs to the front can beat F turns that leave them at the back. Of two equal pairs, the one into a back slot wins, since it leaves the front slots open.
  - **Lookahead**: totals count each later step's look. Every candidate is judged up to the same number of pieces, so an XCross is judged over one step fewer than a cross. It wins when it costs less than the cross plus the first pair and that pair's look, which it does unless that pair is quick and in sight.
  - **Planning in inspection**: a solve's first step is planned in inspection, so it pays no look for its own pieces. In the human style it pays instead for each piece it plans beyond its smallest alternative (`inspectionLook`: `plan`, 2, plus `planHidden`, 3, times how much of those pieces is out of sight on the scrambled cube as held), so an XCross's pair costs 4 to plan in plain sight and up to 10 out of sight, and a cross nothing. The efficiency style pays none of it. Without it, on seeded scrambles, a first step judged to the end of the first two layers took a double or triple XCross on all 16 scrambles tried, and one judged over a cross and one pair took a single XCross on all 8. With it (one pair ahead) 4 of those 8 were a plain cross and 4 an XCross of 8 to 10 moves; with twice the cost all 8 were a plain cross.
  - **Flips**: a searched answer written with wide or slice turns pays a look in plain sight (`flip`, 2) when a step comes after it: they move the centers in the middle of the answer, so the next step's pieces the solver was tracking are somewhere else. That's a wide turn made up by a rotation (`y2 x2 R U R2 B' Rw2 D'`, `y2 R' F' Rw2 U' R2 x2`) as much as wide and slice turns that undo each other (`y D U M D U2 Rw`). Their turns alone cost no more than face turns with a finger regrip, and a rotation before a solve's first turn is free, so before this 11 of 16 seeded crosses of the CFOP example (x and z turns, any front) were written that way, and none is now: `y D U M D U2 Rw` (9.9) became `y' D L U B R F2` (10.75), and on average the crosses went 8.87 → 9.60 to turn and 0.82 → 0.42 s to rank. In whole runs (6 seeded solves each of the ZBLL example and plain CFOP), 11 crosses were written with wide or slice turns before and 1 is now: the ZBLL example's lookahead keeps `y2 F2 Fw' R' Fw R F'` after paying the flip, since its plain writing turns `B' D' B`. Turning went 60.6 → 61.6 and 68.0 → 69.4 per solve, and moves 42.2 → 40.3 and 58.2 → 54.7. Whole solves took longer on average (9.8 → 14.2 s and 3.3 → 4.6 s), from the other cases the later steps then meet (one solve's searched ZBLL alone took 18 s); timed back to back on the same solves, the scoring itself is as fast as before. Moves a step searches with (Roux's `M`) and tilts (`x … x'`) don't pay it, and neither do algs from a set (made as learnt) or a method's last step (nothing to look for after it). A step with *Lookahead style* efficiency pays no looks at all, flips included.
  - **Measured**: on 12 seeded scrambles (Node), *CFOP (cross or XCross, lookahead)* through F2L took an XCross 0/12 times before and 11/12 now. The one cross left had already solved a pair by itself. Turning cost went 38.3 → 33.3 and looks 9.8 → 7.3, so 48.1 → 40.5 in all (the same eyes scoring both). Moves went 30.3 → 26.3, and time 2.9 → 4.6 s per solve, because XCross answers are now listed to their own extra moves and judged. A method ranked by moves gives exactly the same answers.
- **Limits**: every sequence starts with both hands at home, so a method's steps aren't chained (its Total scores the whole solution in one go, which isn't the sum of its steps' scores); the hands only get in each other's way through the awkward-grip and twisted-grip surcharges; the model doesn't know which algs are drilled, so a searched last-layer step can come out as an alg nobody learns (which is what alg sets are for); the eyes don't know how far ahead a solver really tracks, or that a long XCross is hard to plan in 15 seconds; and all the numbers are first guesses to tune against real solving. `fingering(moves, hands)` takes a map of your own.

## Method files

A method is plain JSON, the same in saved methods, exported files and `src/demo/example-methods.json`:

```json
{
  "name": "CFOP (cross + 4 pairs)",
  "steps": [
    { "name": "Cross", "pieces": "DF DR DB DL", "keep": false, "grips": { "bottom": ["D"], "anyFront": true }, "offsets": "", "solvableWith": "", "moves": ["U", "R", "F", "D", "L", "B"], "maxDepth": null, "firstFound": false, "lookahead": 0, "extraMoves": 1, "rank": "speed", "wideAxes": "x z", "sliceAxes": "x z", "rotationAxes": "x z" },
    { "name": "Pair 1", "pieces": "DFR FR | DFL FL | DBR BR | DBL BL", "keep": true, "grips": { "bottom": ["D"], "anyFront": true }, "offsets": "", "solvableWith": "", "moves": ["U", "R", "F", "D", "L", "B"], "maxDepth": null, "firstFound": false, "lookahead": 0, "extraMoves": 3, "rank": "speed", "avoid": "F B" }
  ]
}
```

`pieces` and `offsets` use the same text as the form, with ` | ` between a step's alternatives (e.g. `"DF DR DB DL | DF DR DB DL DFR FR"`; a list of goal texts is read the same way); `solvableWith` holds the *Solvable with* moves (e.g. `"R U"`, `""` = none); `maxDepth` is `null` for no limit; `lookahead` is how many later steps judge the step's answers (0 = none; an answer that already did a later step's part, like an XCross, is judged over fewer, so every candidate ends at the same number of pieces, and a step left with nothing to do, like a pair an XCross already did, is passed over), `candidates` how many of its answers they judge, best first (0 or left out = 64, the most), and `extraMoves` how many moves longer than its shortest a candidate may be; `rank` is what the step's best answer is, `"moves"` (the fewest moves, the default) or `"speed"` (the fastest to turn, see *Speed*); `avoid` holds faces the answer avoids when it can (e.g. `"F B"`, `""` = none): an answer that turns none of them and needs no rotation that costs comes first among those compared, and when avoiding them takes a rotation the ranking decides; `wideAxes`, `sliceAxes` and `rotationAxes` hold the axes its answer may make wide turns, slice turns and rotations about, by speed (e.g. `"x"`, `"x z"`, `""` = none; `sliceAxes` and `rotationAxes` left out = the same as `wideAxes`, as files from before they were apart mean); `style` is how a step ranked by speed counts the solver's eyes in a method, `"human"` (finding pieces, turning the cube mid-answer and, on a solve's first step, planning more than its smallest alternative in inspection cost; the default) or `"efficiency"` (turning only); `algs` names an alg set the step is answered from (`"OLL"`, `"PLL"`, `"ZBLL"`; `""` = none, the step is searched), see *Alg sets* under *Speed*.

The blindfolded fields are:
- `untouched` (`true` = every other piece stays as it is),
- `buffer` (e.g. `"UF"`, `""` = none; implies `untouched`, and `pieces` must be `""`),
- `targetsPerStep` (default 2),
- `parity` (e.g. `"UFR UBR"`, `""` = none),
- `repeat` (`true` = run the step until it has nothing left to do).

A 3-style edges step is `{ "name": "Edges", "pieces": "", "buffer": "UF", "targetsPerStep": 2, "parity": "UFR UBR", "repeat": true }` (the other fields default). Left-out fields get defaults (D bottom, face turns, no offsets or solvable-with moves, nothing untouched, no lookahead, fewest moves, no repeat), and a bad field is reported with its step number.

## Using the engine in another app

The engine (`src/engine/`) has no page code: the test bench (`src/demo/`) is just one app on top of it. Everything a page needs comes from `src/engine/index.ts`. Another app brings three small scripts of its own, like the test bench's in `src/demo/page/`:

```ts
// The app, page side: say how the search worker is started, then use the engine
import { loadEngine, solveStep } from "./engine";

await loadEngine({ searchWorker: () => new Worker("search-worker.js", { type: "module" }) });
const result = await solveStep("R U R' U' F2 D L2", "DF DR DB DL");
console.log(result.solution.toString());
```

```ts
// search-worker.ts: the search worker's script
import wasm from "../search/pkg/puzzly_search_bg.wasm";
import { runSearchWorker } from "./engine/worker/search-worker";

runSearchWorker({ wasm, helper: () => new Worker("search-helper.js", { type: "module" }) });
```

```ts
// search-helper.ts: helper workers for long searches (optional: without `helper` above, every search stays on one core)
import wasm from "../search/pkg/puzzly_search_bg.wasm";
import { runSearchHelper } from "./engine/worker/search-helper";

runSearchHelper({ wasm });
```

- `wasm` is the compiled Rust search code: its bytes (esbuild's binary loader, as here), a URL to fetch it from, or a compiled module, so it works with any bundler.
- `loadEngine` also takes `workerIdleMs` (how long an idle search worker is kept, default 60 s). `runSearchWorker` also takes `maxHelpers` (default 3) and `tableDatabase` (the IndexedDB database built tables are stored in, default `puzzly-tables`; `null` = don't store them).
- A step search without a `searchWorker` stops with a message; reading goal text, checking answers (`reachesGoal`), scoring moves (`fingering`, `speedCost`) and the other text helpers work without one.
- `searchWorker` and `helper` may return anything shaped like a Worker (`postMessage`, `onmessage`, `onerror`, `terminate`): the benchmark runs the search worker in the same Node process that way (`bench/setup.ts`).
- Keep `src/engine/` and `search/` (with its built `pkg`) side by side: the worker modules import the Rust glue from `search/pkg`.

| `src/engine/speed/` | How a move sequence turns in the hands (see *Speed*), from move text alone, and what finding a method step's pieces costs. `look.ts`: the eyes (`LOOK`: a step's look by how much of its pieces is in sight, and the next step's after an answer). `hands.ts`: the hand map (each finger's turns and costs per wrist position, and the costs of wrist turns, regrips and rotations). `writings.ts`: the ways an answer's face turns can be written with wide and slice turns that cancel out. `fingering.ts`: `fingering` (the cheapest way to make a sequence: who makes each move, its score and its other ways), `speedCost`, `cheapestWriting` (the cheapest of those writings), `fingeringText` |
| `src/engine/worker/` | The search worker. Page side: `client.ts` (starts it the way the app says, sends requests, stops it after 60 s idle) and `protocol.ts` (the messages). Worker side: `search-worker.ts` (`runSearchWorker`: measures each combo's distance before searching, searches, lists every answer up to a length for lookahead, or a page of one length for the method search), `solvers.ts` (an exact table for small goals, split tables + IDA* for bigger ones, always on their biggest plan, twips as the fallback; kept up to 256 MB), `table-store.ts` (tables of 100k+ states stored in IndexedDB), `limits.ts` (table sizes and memory budgets), `parallel.ts` (helper pool for long split searches: a short solo search first, then each big IDA* round cut by its first two moves and handed out to the helpers and the search worker, keeping the single-search answer) and `search-helper.ts` (`runSearchHelper`: holds table copies, plans each goal like the search worker, searches the round tasks it's sent) |
| `src/demo/` | Test bench page code. `app.ts`: wires the form and starts the page. `dom.ts`: page elements. `status.ts`: status line. `form.ts`: reads the step form. `chips.ts`: piece chips and presets. `viewer.ts`: 3D cube. `results.ts`: result panel and runs tables. `solve.ts`: scramble and solve. `step-form.ts`, `method-editor.ts`, `method-run.ts`: the method panel. `method-store.ts`: example, saved (localStorage) and file methods. `example-methods.json`: example methods, as data only |
| `src/demo/page/` | What the dev server and the build serve: `index.html`, `index.css`, and the page's three scripts, each bundled as its own file: `main.ts` (starts the page), `search-worker.ts` and `search-helper.ts` (the engine's worker and helper with this build's Rust code) |
| `search/` | Rust search crate: `src/table.rs` exact distance tables and their saved bytes (`table/fill.rs` fills them), `src/coords.rs` their state numbering (`coords/orbit.rs` reads an orbit from the targets, `coords/rank.rs` ranks its states, `coords/tables.rs` its turn tables, `coords/part.rs` orbits numbered together), `src/split.rs` split tables + IDA* (first answer, or every answer up to a length, or a page of them, or one round through given first moves for parallel searches; BLD goals also get whole-orbit tables; `split/plan.rs` picks each sub-table's pieces, `split/relabel.rs` turns a pattern into a sub-table's, `split/driver.rs` deepens one bound at a time, `split/ida.rs` is one IDA* run), `src/symmetry.rs` cube rotations that keep a step's moves (rotated copies of a sub-goal, from any goal, read through one table), `src/solvable.rs` targets closed under a step's solvable-with moves (and the targets' JSON options), `src/lib.rs` twips searches; built to `search/pkg` by `npm run build-search` |
| `bench/` | Node benchmark of the search (see *Benchmark*): `record.ts`, `replay.ts`, `compare.mjs`, `setup.ts` (runs the search worker in the same process), `helper.ts` and friends (search helpers in real threads), `known-algs.ts` and `known-cases.ts` (the speed model against known algs), `alg-sets.ts` (the alg sets against every last-layer state), `zbll-sheet.ts` (`zbll.ts` made from an alg database), `build.mjs` |
| `script/build.js` | Dev server and build (barely-a-dev-server + esbuild), serving `src/demo/page` |

## Browser support

Needs a modern browser (roughly iOS/Safari 15.4+, recent Chrome, Edge or Firefox), because cubing.js uses Web Workers, WebAssembly and WebGL.
