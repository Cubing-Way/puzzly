# puzzly

A Rubik's cube engine built on [cubing.js](https://js.cubing.net/cubing/), with a browser test bench for its scramble, step and full solvers.

## Run

```bash
npm install
npm run dev
```

Then open http://localhost:1234.

## Build

```bash
npm run build
```

The site lands in `dist/web` as plain static files you can host anywhere.

## Rust search

Step searches run in `search/`, a small Rust crate built to WebAssembly, in one worker that keeps what it builds between searches. A goal small enough for one exact distance table (up to 10M states: cross, EO, CO, EOLine, a Roux first block, ZZ blocks after EOLine…) gets one: it's built once (about 50 ms to 0.6 s), then every scramble is answered with a shortest solution right away, without searching. A bigger goal (XCross, XXCross, first layer, DR, F2L pairs, OLL or PLL that keep earlier pieces…) is split into sub-tables that each fit (the goal with some pieces, or their twists, left out) and searched with IDA*, bounded by the largest sub-table distance: still a shortest solution, e.g. XXCross in a few ms instead of up to 9 s, or an OLL step that keeps F2L in about 0.1–0.5 s instead of ~20 s. Sub-tables are planned two ways and both are kept: one fills each table with pieces of its first piece's kind first (all corners together, which sees a PLL's corner cycle or a DR finish's corners), the other with the pieces the same moves turn (a pair's corner and edge share two faces, so F2L pairs are seen whole); either way alone left 2–13× more search nodes on some goal (PLL with keep, XXXCross, F2L pairs). Equal sub-goals share one table (all CFOP pair steps share their "cross + one piece" and "pair + nearby pieces" tables). Sub-tables that are rotated copies of each other are built only once, whatever goal they come from: the cube is turned by a rotation that keeps the allowed moves before the lookup, so one table answers both "cross + DFR" and "cross + DBL", and the table for "4 U edges + DF" also answers for "+ DR" (PLL with keep: 4 tables read 22 ways). The benchmark's methods need 48 tables instead of 84 (69 MB instead of 111), with the same answers and search speed. Each split goal starts on small sub-tables (up to 1M states, built in a fraction of a second) and moves up to bigger, sharper ones one size at a time (10M, then 40M), each time its searches have cost about as much as building the next size would. 40M tables make the heaviest searches (XXXCross, PLL that keeps F2L, BLD flips) about 3× faster, but one method's set can take ~220 MB, so only devices whose browser reports 8 GB of memory or more go past 10M (Chrome and Edge report it, rounded down: a 6 GB PC counts as 4; Firefox and Safari don't, so they stop at 10M). [twips](https://github.com/cubing/twips) is only the fallback for goals that can't be split.

Before searching, the worker measures every alternative × grip: the exact distance from a table, or a lower bound from split tables (their largest distance at the start). Combos are searched closest first, and one that can't beat the best answer so far is never searched, so most steps run one or two searches (a pseudo-cross with any bottom face and any front: 4 searches instead of 82). A step's offsets share one table that holds every offset's target, so a pseudo-cross or a pseudo pair is one search per grip instead of one per offset.

For lookahead (see *Method* below) the same tables also list every answer up to a length, not just the first: IDA* keeps going after a hit (shortest answers first, then one move longer…), skipping answers that pass through the goal on the way (a shorter answer plus moves that keep the goal, which the next steps can always make themselves). Listing is fast (Node, 4 scrambles): every shortest cross or pseudo cross in under 1 ms, the 17–500 one move longer in 0.2–11 ms, a pseudo XCross's answers up to two moves longer (250–5,000 of them) in 10–180 ms. A list can also come a page at a time: the answers of one length that come after a given answer (answers come in a fixed move order, so the next page picks up where the last one ended without redoing it). The method search (see *Method search* below) uses that, so it never holds a huge list.

A step with *Solvable with* moves (see *Test bench*) sends them along with its targets: the Rust side closes the targets under those moves (every pattern they reach from them, at most 100,000) and fills the tables from all of them at once, so the answer is still a shortest one. Split goals of this kind also get one table per piece type holding every tracked piece's position (no twists), because such goals limit how the pieces sit as a whole (a 2-gen corner permutation), which tables of a few pieces can't see. A CP line (`DL DFL DBL` plus the other corners `:p`, solvable with R U) is one exact table of 8.7M states (about 1.7 s to build once, then stored), and each scramble's 4–6 move answer takes ~0.1 ms.

A goal with relative groups (`:r`, see *Test bench*) needs nothing new on the Rust side either: the engine sends one target per way its groups can sit (a pair: 24, or 16 with the cross kept, since the pair can't sit on a cross spot), and the tables fill from all of them at once, so answers stay shortest. Cross + a pair joined anywhere is one search of ~10 ms once its tables exist (~0.35 s with the first build).

Blindfolded (BLD) steps keep every other piece exactly as it is, so their goal depends on the scramble. The engine renames the pieces so the wanted end state *is* the solved cube (moves act on spots, not on piece names, so the answer is the same): every BLD step becomes "solve the whole cube" from a cube that's solved except for a 3-cycle, a parity swap or a flip. All BLD steps of every scramble therefore share one set of tables. They also ask for a whole-orbit table (all 8 corners, 88M states, ~7 s to build once, then stored), which sees corner swaps and twists that tables of one corner each can't. 3-cycles take a few ms and parity steps (13–14 moves) 0.01–6 s. Pure 2-edge flips (13–14 moves) are the slow case, 5–40 s, since no table that fits sees them well. The engine remembers every BLD answer while the page is open, and a case doesn't depend on the rest of the cube, so a repeat of the same case is instant.

A table takes a quarter byte per state (10M states = 2.4 MB): it keeps each state's distance mod 3, since one move changes a distance by at most one, so the search works out exact distances from the start's (found by walking down to the goal) move by move. Tables of 100k states and up are stored in the browser (IndexedDB, database `puzzly-tables`), so after a reload they load in a few ms instead of being rebuilt (e.g. CFOP + OLL: about 3 s the first time, under 1 s after a reload). While the worker builds or loads tables, the status line says *building tables…* / *loading stored tables…*, and the final status says how many it built or loaded. After 60 s without searches the worker stops, so its memory goes back to the system; the next search starts a fresh one, which loads the stored tables. Clearing the site's data in the browser removes them (they're rebuilt when needed).

Long searches use more than one core. A split search first runs alone in the worker for up to 20k search nodes (~60 ms), and almost every search ends there. A longer one carries on from where it stopped, one IDA* round (one answer length) at a time. Each big round is cut into tasks by its first two moves (~240 with face turns), handed out one at a time to helper workers and to the worker itself. There is one helper per extra core the browser reports, at most 3, started on the first long search. A round's answer is the one under the first task (in move order) that has one, so every answer is exactly the one a single search gives; tasks after it aren't waited for. Each helper gets its own copy of the tables of the goals it helps with (sent once by the worker, up to 128 MB per helper, 256 MB on 8 GB devices). On a 2-core / 4-thread laptop, heavy searches run 1.4–1.75× faster (XXXCross 0.86 → 0.55 s, PLL that keeps F2L 2.1 → 1.2 s, a BLD flip 3.2 → 1.7 s); the first long search after the worker starts pays ~0.3 s to start the helpers. Lists (lookahead, method search) and table builds still use one core. Where a worker can't start workers of its own, searches stay on one core.

Build it once before `npm run dev` / `npm run build`, and again after changing it (needs Rust, the `wasm32-unknown-unknown` target and wasm-pack):

```bash
npm run build-search
```

## Benchmark

`bench/` times the search on heavy goals in Node (no browser), so a change to the Rust search or the engine can be compared with the code before it. Bundle it after `npm run build-search`:

```bash
npm run bench-build
```

- `node bench/out/record.js [requests file] [scenarios] [passes]` runs five scenarios on fixed seeded scrambles through the real engine and worker: *dr-finish* (DR, then the whole cube with `U D R2 L2 F2 B2`), *xxxcross*, *cfop-oll-pll* (the CFOP example plus OLL and PLL that keep F2L), *pseudo-lookahead* (the pseudo-slotting example) and *bld-flip* (two pure 2-edge flips). It prints each run's moves and time, twice (first with table builds, then warm), and saves every request the engine sent to the worker (default `bench/out/requests.jsonl`). A full run takes 10–20 minutes. Node reports no device memory, so the worker keeps 10M tables; `DEVICE_GB=8` makes it act as on an 8 GB device. The worker sees one core unless `CORES=4` is set: then it starts 3 search helpers in real threads (`bench/out/helper.js`), as on a 4-core device.
- `node bench/out/replay.js [requests file] [results file] [scenarios]` sends those requests straight to the Rust search, each goal on its biggest tables, and prints per scenario: time, search nodes, µs per node, and how far the start bound is below the real answer length. Tables are saved in `bench/out/tables` after the first run (`FRESH=1` builds them again). Split goals use 10M sub-tables, or `BIG=40000000` for the 8 GB size. `CORES=4` spreads long searches over 3 helper threads, the way the worker does (default 1: one core).
- `node bench/compare.mjs before.jsonl after.jsonl` checks that two replays give the same answers (and node counts) and prints the speed-up per scenario.

The replay bundle carries the Rust search code it was built with, so to compare a Rust change: record once, copy `bench/out/replay.js` to `bench/out/replay-before.js` and replay with it into `before.jsonl`, then change the code, run `npm run build-search` and `npm run bench-build`, replay into `after.jsonl` and compare.

## Test bench

- **Start position**: a random scramble, or any moves you type (Ctrl+Enter solves).
- **Result**: the solution plays on the 3D cube, with move count, time and a check that it really reaches the goal. *Speed* is the solution's speed cost with its regrips (see *Speed*). Under it, *Fingering* lists every move (and regrip) with the hand and finger that makes it, its score (with its finger regrips and its surcharges for an awkward or twisted grip or a layer turned again named), the other ways to make it from that hand position with their scores, and where both wrists are after it; it ends with the hands that have to come back home. *Answers compared* lists the other answers the step found (see *Best answer*), each with its moves, speed and check: click one to see it on the cube, and *Continue from here* then goes on from that one. The runs and method tables have a *Speed* column too. The status line notes when tables are being built or loaded, and how many.
- **Done so far**: moves earlier steps did after the scramble; *Continue from here* adds the shown solution here, so steps can be chained (cross, then XCross…). The scramble is judged by its centers; after it only x/y/z change the grip, so M/E/S in a step don't make the next step think the cube was turned.
- **Runs**: every solve this session; click a row to see it again.
- **Goal**: *Step* solves only the chosen pieces (presets, or the chips with *Chip click sets*). `UF` = solved, `UF:p` = in place with any twist, `UF:o` = oriented and may swap with the other `:o` pieces of its type (`:o2`, `:o3`… are separate groups, e.g. DR: U/D edges `:o`, E-slice edges `:o2`), `UF:s` / `:s2`… = anywhere in its group with any twist, `UF:r` / `:r2`… = solved relative to the rest of its group, anywhere (see *Relative groups*), `UF:x` = its spot may change (for *Blindfolded* steps; anywhere else it's the same as leaving the piece out). Pressed chips show their role (`:o`, `:p`, `:r`, `:x`…). Centers `U L F R B D`: none listed = all six kept, otherwise only the listed ones (e.g. Roux first block `L DL FL BL DFL DBL` with M allowed). *Full cube* solves everything.
- **Relative groups**: `:r` (and `:r2`, `:r3`… for separate groups) marks pieces that only need to be solved relative to each other, anywhere on the cube: `DFR:r FR:r` is that pair joined anywhere, `DF DR DB DL DFR:r FR:r` (preset *Cross + front-right pair joined anywhere*) the cross plus that pair joined wherever it doesn't break the cross, `DBL:r DB:r DL:r BL:r` a corner and its three edges as a block anywhere (an FMC pseudo-block). A group may sit wherever turning the whole cube would put it (24 ways), but only on spots of pieces the goal ignores, or of `:o` / `:s` group pieces, which then take the spots it left; pieces without `:r` stay home, and two groups are placed independently. Answers are still shortest (Node, seeded scrambles): a pair joined anywhere 2–3 moves (2–5 into its slot), cross + pair joined 6–7 (XCross 7–9), the block anywhere 5–6 (6–7 at home), each in about 10 ms once the tables exist; cross + two pairs joined (`:r` and `:r2`) 7–8 moves in ~90 ms. With restricted moves, places the moves can never reach are left out (a pair in a slot R U never turn, an edge flipped under U R L). In a method, *Keep earlier steps' pieces* keeps each earlier group joined on its own (groups are renumbered, so a pair joined earlier and one joined now don't have to sit together, and a step joining "the easiest pair" with *any front* skips pairs already joined); to grow a block instead, list its pieces again in the new step's group, e.g. `DBL:r DB:r DL:r BL:r`, then `DBL:r DB:r DL:r BL:r DFL:r DF:r FL:r` (a pseudo 2x2x2, then 2x2x3: 10–13 moves on 4 scrambles vs 11–13 for the same blocks at home).
- **Alternatives**: put several goals in *Pieces*, one per line (*+ Alternative* copies the caret's line below it); any one of them counts. The chips, preset and cube mask follow the line the caret is on, and Enter adds a line (Ctrl+Enter solves). Every alternative × grip (with all its offsets) counts and the shortest wins (combos that can't beat the best aren't searched); on a tie, the alternative that solves more new pieces wins, so `DF DR DB DL` plus a line `DF DR DB DL DFR FR` gives the XCross whenever it costs no extra move. The result's *Alternative* (e.g. 2 of 2), the status line and the runs table say which one won.
- **Bottom face**: which faces may go on the bottom, with beside them the turns an answer may start with: *any front* (y turns), and by speed *x turns* and *z turns* (see below). Every grip counts and the shortest answer wins; it starts with the rotation to do first (e.g. `x2 L D R D`).
- **Offsets**: the goal also counts when the cube is off by one of these moves, e.g. `D D2 D'` (*ADF*) for a pseudo-cross or `U U2 U'` (*AUF*) for a last-layer step. Spaces separate one-move offsets; use commas when an offset has several moves (`U D, U2`). No offset is always tried too; a grip's offsets are searched together (one table holds every offset's target) and the shortest wins. With *finish with the move that undoes the offset* ticked (the default), a step solve's answer ends with that move, so it counts in the moves and the speed, and the best answer is the shortest or fastest with it: a pseudo-cross one move short of the cross no longer beats a cross of the same length. Unticked, the solution leaves the offset in: the result shows it with the moves that undo it, and a next step needs the same offsets (or those undo moves first). A method step always leaves its offset in, for the steps after it.
- **Solvable with**: the goal also counts when these moves alone can finish it later, e.g. `R U`: `DL DFL DBL UFR:p UBR:p UBL:p UFL:p DFR:p DBR:p` solvable with `R U` is the left line plus corners that R and U alone can solve (the CP step of 2GR or ZZ-d), not the corners in place. Every cube state those moves reach from the goal counts (at most 100,000: give pieces the moves twist anyway `:p`, as above, which leaves 120 states instead of 29,160). The result and the runs table check the answer the same way. Later steps that keep earlier pieces only keep the ones those moves can't disturb (the line here, not the corners), so the steps after it should use those moves only (e.g. *Moves allowed* R U), which keep the property by themselves. If the moves would change pieces (or centers) the step's allowed moves never touch, the step stops with a message instead.
- **Blindfolded**: *keep every other piece untouched* makes every piece the goal doesn't list stay exactly where it is, turned the same way (instead of being ignored).
  - The listed pieces go home, and the pieces they push out fill the spots they leave. `:p` pieces may end with any twist, and `:x` spots may take any piece.
  - Examples: `UR UB UF:x` finds the shortest 3-cycle that solves UR and UB through UF; `UFR:p UBR:p UR UL` finds the shortest T-perm-like swap.
  - A goal no moves can reach with everything else kept (a lone swap or a lone twist) stops with a message.
  - **Buffer**: the step picks its own pieces (leave *Pieces* empty). It follows the buffer's cycle for *targets per step* targets (2 = a 3-cycle): each target sends the piece in the buffer home and brings the piece there into the buffer.
  - When the buffer holds its own piece, a new cycle starts at any unsolved piece; every choice is tried and the shortest wins. With the buffer home, a step may instead fix two pieces that are only flipped or twisted in place, like a flip alg.
  - **Parity pieces** (e.g. `UFR UBR`): when the targets left are odd (a lone swap no moves can do), those pieces swap too, keeping their twists (like a parity alg). Only if that can't work may they end any way.
  - Quick picks: *Edges (UF)* (parity `UFR UBR`), *Corners (UFR)*, *None*. The result shows which pieces went home and which spots changed, and the check also makes sure every other piece is still where it was.
  - Untouched steps take no offsets or solvable-with moves. Their goal is relabeled to "the whole cube" (see *Rust search*), so they share one set of tables.
- **Moves allowed**: face turns plus M, E, S. A letter allows every turn of that layer (R, R2, R'); the second row (`U2` … `S2`) allows only its half turn (ticking both = every turn). Quick picks: *Face turns*, *R U*, and *DR* (`U D R2 L2 F2 B2`, a domino reduction's second phase). E.g. after your own DR step, a step with every piece, *Keep earlier steps' pieces* and *DR* finishes the cube without leaving DR, shortest within those moves (12 scrambles: 12–15 move finishes; the first few solves take 1–2 s while the tables are built, then finishes take 6–260 ms). In method files these are plain moves like `"R2"`. If a step keeps centers that are out of place and its moves can't bring them home, it stops with a message instead of searching forever.
- **Best answer**: what wins among a step's answers. *Avoid faces* (e.g. `F B`) comes first: among the answers compared, one that turns none of those faces and needs no cube rotation that costs comes before all others, whatever its length or speed, so give such answers room with extra moves. It's for first-two-layers pairs, where an answer on R, U and L turns faster and takes almost no regrips. When avoiding the faces takes a rotation, the ranking decides: by speed a rotation costs 2.5, so `F' U' F` (4.6) beats `y' R' U' R` (5.5) in the middle of a solve, while on a solve's first step, where the rotation is free, the answer on R and U wins. Then: *Fewest moves* (the default) takes the shortest, as before. *Speed* takes the one with the lowest speed cost (see *Speed*); on a solve's first step (nothing in *Done so far*) a grip rotation costs nothing, so with *any front* ticked it picks the front too. *x turns* (beside *any front*, on by default) also tries each answer with one R or L turn made as the other hand's wide turn (R' as Lw' after an x), and *z turns* the same with F and B (Fw, Bw): an x or z turn first, or last, makes up for it, so the cube ends exactly as the plain answer leaves it. *Add form as step* saves them with the step (`wideAxes` in a method file), and the method's rows then show the wide writing, like a step solve. So *Solve* and *Run method* give the same cross when the form and the step say the same. *Up to N extra moves* also compares answers that many moves longer than the shortest: by speed one of them may win, and a method step's lookahead judges them too. *List N other answers* shows that many more under the result, best first (shortest first, or fastest first by speed); 0 lists none, which is the fastest search (a long last-layer step takes several times longer when it has to list its answers).
- **Method**: a list of steps run in order, each from where the last one left the cube (after *Done so far*). The form on the left is the step editor: set it up, give the step a name, then *Add form as step*; *Edit* loads a step back into the form and *Update step N* saves it. *Keep earlier steps' pieces* adds every earlier step's pieces to the goal (this step's roles win; centers only change when the step lists some). Only the grips where the fewest of the step's pieces are already kept get searched, so a grip turn can't swap the step's pieces for ones already done: `DFR FR` with any front means "the easiest pair not done yet", and an OLL step can't turn the solved first layer to the top. A step whose pieces are all done already in the grip it's held in (e.g. the last pair after an XCross) answers with 0 moves. *Repeat until done* runs a step again and again, until a round has nothing left to do (0 moves); each round gets its own row (*Edges 1*, *Edges 2*…). That's one 3-cycle per round for BLD, or "the easiest pair" with *any front* until F2L is done. *Run method* lists each step's solution and moves; click a row to see it on the cube. *Save* keeps the method in this browser; *Export file* / *Import file* share it as JSON.
  - Examples (19, each from scramble to solved): CFOP (cross, 4 pairs, OLL, PLL), also with a cross-or-XCross first step judged by lookahead, with pseudo-slotting (pairs up to ADF, then an ADF step), with ZBLL (last pair + EO, then one look) and as CFCE (CLL, ELL); a beginner layer-by-layer method; Roux; ZZ (EOLine, blocks, ZBLL) and ZZ-CT; Petrus; Heise; LEOR; Mehta; corners first; two-phase (domino reduction, then finish) and four-phase (EO, domino, half-turn reduction, finish); two blindfolded methods.
  - In 14 of them the steps before the last layer rank by speed (*Best answer*: Speed, with one extra move), and a first step picks its front, which costs nothing. Each step that fills a first-two-layers slot (a pair, its corner or its edge) lists all four slots as alternatives (`DFR FR | DFL FL | DBR BR | DBL BL`), so it inserts where the pair is and needn't turn the cube to bring it to the front right. The crosses of the CFOP-style and beginner examples may make an R or L turn as the other hand's wide turn (*x turns*; on the scramble under *Speed* the cross is then `y2 x' L' U L2 Lw' F`, 6.4, where it was `R' F R2 L' B`, 8.0), except in the lookahead example, where that took about 5 s a solve. The CFOP-style pair steps also avoid F and B, with two extra moves to find answers without them (one in the lookahead example, none in pseudo-slotting and *Last pair + EO*, which would get slow).
  - Over 6 scrambles each, those steps' speed cost fell by about 20% on average: CFOP's cross and pairs 53.4 → 40.1 (`y2 U2 B' R2 B R2` became `U L U' L2 U' L`), the cross-or-XCross lookahead 49.4 → 32.6, the beginner method 88.6 → 63.4, Roux 63.9 → 55.9, ZZ 42.9 → 34.8, Petrus 41.3 → 39.6. In CFOP the pair steps that turn F or B went from 19 of 24 to 5 of 24, and those that start by turning the cube from 22 of 24 to 1 of 24, for 5 more moves (28.0 → 33.3) and about 2 s a solve (the lookahead example about 3 s); Roux and ZZ take no more moves. Last-layer steps that keep everything else, Corners first, the two-phase and four-phase methods and the blindfolded ones still take the fewest moves: listing all their answers to rank them takes too long (Corners first: 10–40 s a step).
  - Last steps that keep everything else and use face turns (PLL, ZBLL, COLL…) get slow as their answers get longer: up to 11 moves well under a second, 13–14 moves from 10 s to over a minute. The ZZ-type examples use `U R L` for their last step, which takes a few seconds at most.
  - ZZ (left block + CP, then R U only): the left block step also leaves corners R U can solve, so the right block and the last layer use only R and U. Without it, 5 of 6 test scrambles end with *No solution found!* at the last layer.
  - 3-style BLD: edges from buffer UF with parity `UFR UBR`, then corners from UFR, each repeated until done. On 12 random scrambles: 81–116 moves, every round checked. The first run takes ~10 s (table builds). After that most solves take 0.1–3 s, and a first-time 2-edge flip takes up to ~30 s.
- **Lookahead** (per method step, under the step name): on its own, each step takes its shortest answer, so a method never accepts a slightly worse step that sets up the next ones. With *Lookahead N steps*, the step lists its candidate answers (every alternative × grip × offset: all its shortest answers, plus answers up to *extra moves* longer, at most 64, shortest first), runs the next N steps after each one (each taking its own shortest answer), and keeps the candidate with the fewest moves in total; on a tie, its own shortest answer stays. That's what makes pseudo-slotting and free XCrosses pay off: a pseudo pair that leaves the cube off by a D turn, or an XCross two moves longer than the cross, wins when it saves more in the next step. The results table's *Lookahead* column shows candidates compared → the winner's moves over the steps it was judged by (details on hover). On 8 scrambles, total moves greedy → lookahead 1 (→ with 1 extra move): pseudo-slotting 218 → 197 (→ 183), CFOP 227 → 211 (→ 188), ZZ 202 → 184 (1 extra move); a step with lookahead 1 plus its next step is never longer than greedy's two. It costs one run of the next steps per candidate: the pseudo-slotting example takes about 0.5–1.5 s per solve once its tables exist. Lookahead 0 (the default, and what old method files get) gives exactly the answers it gave before. *Extra moves* is the step form's field under *Best answer*. A step ranked by speed judges its candidates by speed cost instead of moves: its own plus the next steps', each of those taking its own best answer.
- **Method search** (*Search fewest moves*, under *Run method*, with a time limit in seconds): looks for the run of the whole method with the fewest moves in total, where any step may take a longer answer if that saves more moves later. It counts moves only, whatever the steps' *Best answer* says.
  - It starts from *Run method*'s answer (with the steps' own lookahead) and only looks for runs with fewer moves. Each shorter run replaces the rows as soon as it's found (the *Time* of the total is when it was found), and the best one goes to the cube and the runs table at the end.
  - It goes through each step's answers shortest first. Before going on from an answer, it measures how far the next step is, and how far a later step's goal is from there. For example, after a CFOP cross every run still has to reach F2L. Those goals are worked out from the method alone: the steps' alternatives and grips, which earlier pieces they keep, and every move the steps in between may use. An answer whose rest can't get under the best total is skipped, and so is a cube state reached before with no fewer moves. The last step just takes its shortest answer within the moves left.
  - It stops at the time limit or when you press *Stop search*, keeping the best run. The status shows the fewest moves any run can have (*at least N moves*). When the search gets through everything, or finds a run that short, the status says the run is *the fewest this method can do*; otherwise there may still be a shorter one.
  - Rules: a step's answer never passes through its own goal on the way (as with lookahead), *Max depth* still limits a step, *stop at first answer* is ignored, a repeated step is searched round by round, and the offset the last step leaves isn't counted (a fix step like *ADF* counts like any step).
  - Examples (Node, 30 s after one plain run built the tables; plain run → best found): DR then a `U D R2 L2 F2 B2` finish on 4 scrambles 19 → 19, 23 → 17 (in 0.7 s), 22 → 20, 25 → 20 (in 0.6 s), where cubing.js's two-phase full solver gives 19, 20, 20, 21. CFOP 31 → 20 and 31 → 23, ZZ 23 → 16 and 28 → 17, ZZ with CP and R U 36 → 26 and 42 → 27, pseudo-slotting 23 → 22. Small two-step methods (cross then a pair) finish in under a second and are proven the fewest, often straight from the bound; whole CFOP or DR runs can't be proven in that time (their bound is 7–8 moves, far below the 16–27 a run takes).
  - It measures roughly 1,500 step starts per second. The slow part is listing many long answers of a big step (every 12-move DR takes seconds), so it improves fastest on methods whose steps have few answers of each length.

## Speed

A move count doesn't say how a solution turns in the hands. `src/engine/speed/` scores that: `fingering(moves)` finds the cheapest way two hands can make a move sequence and says who makes each move, and `speedCost(moves)` is its cost alone, where an easy turn (R, or a U flick) is 1. It only reads move text, so it needs no search worker. A step can rank its answers by it (*Best answer* in the test bench, `rank: "speed"` in the engine and in method files); left alone, steps still take the fewest moves, with exactly the answers they gave before.

- **Wrist positions**: each hand is in one of three, named by where its thumb sits: *home* (on the front), *down* (on the bottom: the right hand after R') and *up* (on top: after R). R, R' and R2 are wrist turns of the right hand, L, L' and L2 of the left. A wrist can't turn past *down* or *up*, and a half turn goes from one to the other, so R2 from home takes a regrip first.
- **Hand map** (`HANDS` in `hands.ts`): for each wrist position, the turns each finger can make and what they cost. It lists the right hand; the left hand's tricks are the mirror image (U ↔ U', F' ↔ F…, M turns stay as they are). A turn may have several tricks at one position; the cheapest is used and the rest are its other ways.
  - **The fingers keep their tricks as the wrist turns**, on whichever layers they then lie on. The index finger's U tricks are F tricks with the thumb on the bottom and B tricks with it on top; the ring finger's D tricks are B tricks with the thumb on the bottom and F tricks with it on top (so after L the left ring finger turns B, and after R the right ring finger turns F'); the middle finger's E' is S, then S'. Pushes don't follow: a finger can only push a layer it reaches from behind (U and D at home, and U for the index finger with the thumb on top), so no index push turns F' or B'.
  - **Costs go by kind of trick**, one number each at the top of `hands.ts`: a flick 1 (the finger pulls its layer), a double flick 1.5 (with the finger beside it, a half turn), a push 1.2. The table shows these; what the layer itself adds is under *Layers* below.
  - **Reaches** (marked * below) are tricks a finger has to leave its place for, so each also costs a finger regrip (0.6, counted in the costs shown): F at home with the index finger or the thumb, every slice turn, every push, and D' from the thumb-on-top position.

  | Wrist | Where the fingers lie | Tricks (cost) |
  | --- | --- | --- |
  | *home* | on the back: index on U, middle beside the E slice, ring on D; the index finger also reaches over the top to F | index: U (1), F* (1.6), M* (1.6) · index + middle: U2 (1.5) · index push: U'* (1.8) · middle: E'* (1.7) · ring: D' (1), M'* (1.6) · ring + pinky: D2 (1.5) · ring push: D* (1.8) · ring + middle: M2* (2.1) · thumb: F'* (1.6), M'* (1.6). No F2 and no B |
  | *down* | over the top: index on F, middle beside the S slice, ring on B | index: F (1) · index + middle: F2 (1.5) · middle: S* (1.6) · ring: B' (1) · ring + pinky: B2 (1.5). Nothing on U or D, and no pushes |
  | *up* | under the cube: index on B, middle beside the S slice, ring on F; the index finger still reaches U from behind, and with a longer reach D | index: B (1), U (1), D'* (1.6) · index + middle: B2 (1.5), U2 (1.5) · index push: U'* (1.8) · middle: S'* (1.8) · ring: F' (1) · ring + pinky: F2 (1.5) |

  With the left hand's mirror images most turns have several ways. U after R: the right index finger (1), or a left index push (1.8). F', with its layer's 0.2: the left index finger with the left thumb on the bottom (1.2), the right ring finger with the right thumb on top (1.2), or at home the right thumb or the left index finger (1.8 each, both reaches).
- **Wrist turns and the rest**: a wrist turn costs 1 (a half turn 1.4). A wide turn costs 0.2 more when a wrist makes it (Rw, Lw) and 0.5 more when a finger does, on two layers (Uw, Fw…). A move no trick makes (E2, S2, notation the model can't read) costs 2.5.
- **Layers**: how well a layer turns from the home grip is added to every turn of it, whoever makes it: nothing for R, U and L, 0.2 for F and D, 0.4 for B. Turning B again in the same sequence costs 1 more each time (`again`): one B is a quick flick (1.4 in all), B after B isn't. So of two ways to hold the same turns, `y2 B U B L' F D` (9.3) loses to `y L U L F' R D` (8.9), though the second takes two more regrips.
- **Regrips and grips**: a regrip (one hand lets go and takes the cube again at another wrist position) costs 1.8 between turns, and 1 when the hand comes back home. Before the first turn one hand regrips for 0.5 (it's done while still looking at the cube), but a second hand pays the full 1.8 there: starting with both hands regripped is awkward. After the last turn each hand that isn't at home costs 1 (it has to come back), so a fingering that ends at home, or nearer to it, wins. Every move made while both hands are away from home costs 0.7 more (an awkward grip: both thumbs on top, or both on the bottom), so bringing a hand home, or tilting the cube back (below), beats turning on in it. With the wrists turned opposite ways the grip is twisted (one thumb on top, the other on the bottom: what R then L, or R' then L', would leave), and that costs 1.2 instead, on the move that ends in it as well as on every move made from it; so the model grips another way first: `R' L'` costs 3.5 with a regrip and never twists.
- **Finger regrips** (0.6, less than any hand regrip between turns): one finger goes somewhere else while the hand keeps its grip. A reach costs one (above). So does a move that needs a finger the move before left out of place, when the same hand made that move and hasn't regripped since: a finger that has to make this move too, or the last finger holding the cube from behind. After D' with the right ring finger, a right-hand U2 (index and middle) has nobody at the back, so the ring finger comes back first: `L D' U2 L'` costs 5.3, the U2 1.5 + 0.6. With the other hand free it makes one of the two moves and nothing is paid (`D U2` at home: left ring finger, then right hand), and a finger is back in its place by itself once another move has been made (in `R U R' U R U2 R'` the index finger is never late).
- **Rotations and tilts**: a rotation costs 2.5, and both hands end at home. Before the first turn of a solve (nothing was done before the step) it's free, since the cube is picked up that way: with several grips allowed (*any front*), a first step ranked by speed also picks the front that turns best. An x turn can also be a tilt, made by both wrists together without letting go: x takes both wrists a step up, x' a step down. A tilt that brings both hands home is free, because nothing moves: after R' and L both thumbs are on one face, and calling that face the front is all the x does. Any other tilt costs 0.5 per quarter turn.
- **Evaluation**: before every move each hand may regrip to any position, and the cheapest whole sequence wins (9 wrist states, each with the fingers the last move left out of place; about 13 µs per move for the cost alone). So a regrip is only paid where no finger reaches the turn, and it's placed where it helps the moves after it too. Each move of the result has the hand and finger that makes it, its own cost (its layer's included), its finger regrips, its surcharges for an awkward or a twisted grip and for a layer turned again, the regrips before it with theirs, the other ways to make it from the same hand position with their costs, and both wrists after it; the result ends with the hands that come back home.
- **Ranking by speed** (`rank: "speed"` in a step's options and in a method step): the step lists its answers, the shortest ones and those up to `extraMoves` longer (up to 1,000 per alternative × grip), gives each its speed cost (grip rotation included, so a `y` first costs 2.5) and takes the lowest; `stepCandidates` gives them fastest first. Each answer is also tried in the other grips that ask for the same thing (a cross with *any front*: the very same turns held with each front, so renamed), as answers of their own: `L' B L' U' F' L2` and `y' F' L F' U' R' F2` are both listed, each with its score. With `undoOffset` (a step with offsets) every answer goes on to undo the offset it reached, and is measured with those moves, by moves as well as by speed: on seeded scrambles the shortest pseudo-cross with its D turn was exactly as long as the shortest cross. With `wideAxes` ("x": R and L, "y": U and D, "z": F and B) each answer is also tried with one such turn made as the opposite wide turn: R is Lw then x, so the left hand turns two layers while the right holds its own still, and nothing is regripped. The cube's turn is made up by a rotation first (free at the start of a solve, the moves before the wide turn then named for the cube held that way) or by a rotation last (which costs one). Either way the cube ends exactly as the plain answer leaves it, so it works for any goal. Such a result has two writings: `wide`, as the hands make it, is what's scored and shown; `solution` says the same with the turn itself and a rotation (`R' x` for `Lw'`), since the engine tells how the cube is held from x, y, z turns alone, and is the one to check and go on from. On the scramble `D2 L' F' B' R' D L D' F' D2 L D2 B2 R U2 F2 R U2 R U2 F2` the fastest cross without wide turns is `R' F R2 L' B` (8.0); with x turns and any front it's `y2 x' L' U L2 Lw' F` (6.4): five turns, no rotation after the start, no regrip, the left hand home again after Lw'. With no extra moves the answer is still one of the shortest. With `avoid` (faces) each answer gets a `tier`, and a lower tier always comes first: 0 turns none of the faces and starts with no rotation that costs (by moves, or on a solve's first step, none costs); 1 turns none after a rotation, or turns some where no answer held the same way does without, so that the speed score decides between rotating and turning them; 2 turns some although an answer held the same way doesn't. A method step with lookahead and rank speed compares speed costs over itself and the next steps. On seeded scrambles (Node): a cross with any front, 7 moves at 13.9 → 7 at 8.8 held with another front, and 6 at 13.2 → 6 at 9.0; CFOP's cross and 4 pairs with 1 extra move, 28 moves at 55.6 → 30 at 48.2, and only 29 at 52.8 → 30 at 52.2 (each step takes its own fastest answer, which can leave the next one a slower start; lookahead is what judges that); a cross with lookahead and the 4 pairs, 26 at 53.5 → 24 at 42.3 and 29 at 59.7 → 25 at 39.9; pseudo-slotting with lookahead, 23 at 46.6 → 25 at 41.8. Ranking a cross takes 50–650 ms and a lookahead method 1.4–6 s per run. The method search (*Search fewest moves*) still counts moves only.
- **Examples**: `R U R' U'` 4 · `R' F R F'` 5 (F with the right index finger 1.2, F' with the right thumb 1.8, a reach) · a T perm (14 moves) 15.4 with no hand regrip · `F2` alone 3.2 (right thumb to the bottom first, and back after) · `L B L'` 3.4 (B with the left ring finger) · `R B R' U R B R'` 8.8 (the second B costs 1 more) · the U perm `R2 U R U R' U' R' U' R' U R'` (11 moves) 15.7 with 4 regrips · the cross `L' B L' U' F' L2` 11.1, or 9.7 held with another front (`y' F' L F' U' R' F2`, the rotation free at the start) · `x' L' U L2 Lw' F` 6.4 (started with x', the R' made as the left hand's wide turn: no regrip, both hands home at the end).
- **Limits**: every sequence starts with both hands at home, so a method's steps aren't chained (its Total scores the whole solution in one go, which isn't the sum of its steps' scores); the hands only get in each other's way through the awkward-grip and twisted-grip surcharges; and all the numbers are first guesses to tune against real solving. `fingering(moves, hands)` takes a map of your own.

## Method files

A method is plain JSON, the same in saved methods, exported files and `src/demo/example-methods.json`:

```json
{
  "name": "CFOP (cross + 4 pairs)",
  "steps": [
    { "name": "Cross", "pieces": "DF DR DB DL", "keep": false, "grips": { "bottom": ["D"], "anyFront": true }, "offsets": "", "solvableWith": "", "moves": ["U", "R", "F", "D", "L", "B"], "maxDepth": null, "firstFound": false, "lookahead": 0, "extraMoves": 1, "rank": "speed", "wideAxes": "x" },
    { "name": "Pair 1", "pieces": "DFR FR | DFL FL | DBR BR | DBL BL", "keep": true, "grips": { "bottom": ["D"], "anyFront": true }, "offsets": "", "solvableWith": "", "moves": ["U", "R", "F", "D", "L", "B"], "maxDepth": null, "firstFound": false, "lookahead": 0, "extraMoves": 2, "rank": "speed", "avoid": "F B" }
  ]
}
```

`pieces` and `offsets` use the same text as the form, with ` | ` between a step's alternatives (e.g. `"DF DR DB DL | DF DR DB DL DFR FR"`; a list of goal texts is read the same way); `solvableWith` holds the *Solvable with* moves (e.g. `"R U"`, `""` = none); `maxDepth` is `null` for no limit; `lookahead` is how many later steps judge the step's answers (0 = none) and `extraMoves` how many moves longer than its shortest a candidate may be; `rank` is what the step's best answer is, `"moves"` (the fewest moves, the default) or `"speed"` (the fastest to turn, see *Speed*); `avoid` holds faces the answer avoids when it can (e.g. `"F B"`, `""` = none): an answer that turns none of them and needs no rotation that costs comes first among those compared, and when avoiding them takes a rotation the ranking decides; `wideAxes` holds the axes its answer may make a wide turn about, by speed (e.g. `"x"`, `"x z"`, `""` = none).

The blindfolded fields are:
- `untouched` (`true` = every other piece stays as it is),
- `buffer` (e.g. `"UF"`, `""` = none; implies `untouched`, and `pieces` must be `""`),
- `targetsPerStep` (default 2),
- `parity` (e.g. `"UFR UBR"`, `""` = none),
- `repeat` (`true` = run the step until it has nothing left to do).

A 3-style edges step is `{ "name": "Edges", "pieces": "", "buffer": "UF", "targetsPerStep": 2, "parity": "UFR UBR", "repeat": true }` (the other fields default). Left-out fields get defaults (D bottom, face turns, no offsets or solvable-with moves, nothing untouched, no lookahead, fewest moves, no repeat), and a bad field is reported with its step number.

## Using the engine in another app

The engine (`src/engine/`) has no page code: the test bench (`src/demo/`) is just one app on top of it. Everything a page needs comes from `src/engine/index.ts`. Another app brings three small scripts of its own, like the test bench's in `src/demo/page/`:

```ts
// The app, page side: say how the search worker is started, then use the engine
import { loadEngine, solveStep } from "./engine";

await loadEngine({ searchWorker: () => new Worker("search-worker.js", { type: "module" }) });
const result = await solveStep("R U R' U' F2 D L2", "DF DR DB DL");
console.log(result.solution.toString());
```

```ts
// search-worker.ts: the search worker's script
import wasm from "../search/pkg/puzzly_search_bg.wasm";
import { runSearchWorker } from "./engine/worker/search-worker";

runSearchWorker({ wasm, helper: () => new Worker("search-helper.js", { type: "module" }) });
```

```ts
// search-helper.ts: helper workers for long searches (optional: without `helper` above, every search stays on one core)
import wasm from "../search/pkg/puzzly_search_bg.wasm";
import { runSearchHelper } from "./engine/worker/search-helper";

runSearchHelper({ wasm });
```

- `wasm` is the compiled Rust search code: its bytes (esbuild's binary loader, as here), a URL to fetch it from, or a compiled module, so it works with any bundler.
- `loadEngine` also takes `workerIdleMs` (how long an idle search worker is kept, default 60 s). `runSearchWorker` also takes `maxHelpers` (default 3) and `tableDatabase` (the IndexedDB database built tables are stored in, default `puzzly-tables`; `null` = don't store them).
- A step search without a `searchWorker` stops with a message; reading goal text, checking answers (`reachesGoal`), scoring moves (`fingering`, `speedCost`) and the other text helpers work without one.
- `searchWorker` and `helper` may return anything shaped like a Worker (`postMessage`, `onmessage`, `onerror`, `terminate`): the benchmark runs the search worker in the same Node process that way (`bench/setup.ts`).
- Keep `src/engine/` and `search/` (with its built `pkg`) side by side: the worker modules import the Rust glue from `search/pkg`.
